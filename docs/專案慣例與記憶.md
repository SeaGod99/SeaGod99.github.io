## 1. 溝通與工作習慣

### 1.1 一律用繁體中文回覆
所有對使用者的說明、摘要、選項、驗收報告一律**繁體中文**，不要夾雜英文句子／標題（曾出現 "Good, preserved" / "Bad, fixed" 被指正）。技術名詞（class 名、函式名、指令、CSS 屬性、commit 前綴如 feat/fix）可保留原文，但敘述句一律繁中。
**為何**：使用者為 FFXIV 台服（繁中）玩家，母語繁中。

### 1.2 終端機用 VSC 內建終端機
下指令時走 VS Code 內建終端機，**避免使用者電腦一直彈出獨立終端機視窗**。

### 1.3 多行 commit／PR 訊息走訊息檔 `-F`
用 **Bash 工具**下 `git commit` 多行訊息時，**不要用 PowerShell here-string `@'...'@`**——Bash 是 POSIX sh，會把 `@` 當字面字元，導致訊息開頭／結尾多出 `@` 行（曾犯兩次都得 `--amend` 修）。
**正確做法**：先用 Write 把訊息寫到 scratchpad 的 `.txt`，再 `git commit -F <path>`（或 `--amend -F <path>`）。本機 CRLF 環境穩定、也避開引號跳脫。

### 1.4 gstack 技能組
本站已裝 gstack 技能組，各使用情境對照表見 [CLAUDE.md](../CLAUDE.md)。常用：`/browse`（開頁截圖驗收）、`/qa`、`/verify`、`/design-review`、`/code-review`、`/ship`、`/scrape`。

### 1.5 UI/UX 設計輔助 Skill（ui-ux-pro-max，2026-08-01 定案）
使用者指定安裝 [nextlevelbuilder/ui-ux-pro-max-skill](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill)（含 ui-ux-pro-max／banner-design／brand／design／design-system／slides／ui-styling 共 7 個技能），裝在**系統層** `~/.claude/skills/`（不進 repo，換機需重裝）。**規則寫在 [CLAUDE.md](../CLAUDE.md)「UI/UX 設計輔助 Skill」一節**：本專案凡碰到畫面相關問題（版面／配色／字體／無障礙／動效／圖表／視覺一致性），一律先呼叫 `ui-ux-pro-max` 取得設計依據，再接 gstack 的 `/design-review` 實際截圖驗收與修復。其餘 6 個技能多為 React/Tailwind 元件或品牌／簡報用途，本站（純 HTML/CSS 無框架）少用。

### 1.6 介面文案：只寫「資料」，不寫「導覽詞」與自我推銷（2026-08-09，使用者三次糾正後定案）

同一輪被連續糾正三次，記下來：

- ❌ 標題加形容詞／自我推銷：「製作計畫**（上下層一目了然）**」→ ✅「製作計畫」。
- ❌ 替 UI 元件解釋它自己：「直購較省（自己做要 1,620 G**，展開可看它的材料**）」→ ✅ 去掉後半，`▸` 圖示已經在講同一件事。
- ❌ 逐列重複的狀態註記：「參考：上層改成買了就不用備」→ ✅ **直接顯示材料**，狀態差異用淡化／徽章表達即可。

判準：**這句話是不是在告訴使用者一個他從畫面看不出來的「數字或事實」？** 是→留（例：「自己做要 1,620 G」「全計畫共需 297」）；只是在描述介面怎麼用、或誇自己設計得好→刪。
唯一例外是**教非顯而易見的互動**（例：計畫清單頂端那句「任何一列按 ✓ 就是我已經有了」），因為那個因果關係（勾了會剪掉整個子樹）真的看不出來。

## 2. 收藏／追蹤頁共通慣例

適用範圍：`/collections/*`、`/minions/`，以及具「追蹤擁有進度」性質的工具頁。

### 2.1 取得方式＝最優先資訊，永遠預設顯示
使用者明確要求：收藏／追蹤頁「最想知道的是**怎麼取得**」，因此取得方式**預設顯示且視覺優先**，不可只靠 hover、不可藏在展開鈕後（舊的點擊展開 `collection-detail.js` 已刪）。
- 各明細卡頁的 `.X-detail` 區塊永遠 `display:block`；金色「取得方式」標籤（`::before`）＋金色左側強調線；空內容 `:empty{display:none}`。
- emotes 同款（置中版型、無左線）；hairstyles 來源本就常駐標籤。
- minions 是密集圖示格：名稱下方加一行金色**來源類別**（永遠顯示），完整細節點 ⓘ 釘選 tooltip。
- **勿改回 hover／toggle。**

### 2.2 共用 CSS：`assets/css/common.css`
收藏類頁面的共用 CSS 已抽成 `assets/css/common.css`（2026-06 重構）。內含版面外框（header/toolbar/filter/progress/footer）、`.col-*` 卡片系統（col-grid / col-card / col-icon / col-name / col-tags / col-detail / src-tag / type-*）。色票 token 已於 2026-08-01 移出到 `tokens.css`（見 §3.6）。
- 各頁 `<head>` 順序（2026-08-01 起全站統一）：`<link tokens.css>` → `<link theme.css>` → `<link common.css>`／`tool-header.css`／`et-bar.css` → 該頁 `<style>`（排最後，覆寫勝出）。**theme.css 不再排在最後**，這樣頁面才有辦法用同特定度的 `:root[data-theme="light"]{…}` 覆寫自己的亮色表現。
- 每頁只在自己精簡 `<style>` 設 **4 個強調色變數**：`--accent`（**寫成 `var(--gold)`／`var(--purple)` 這種指向色票 token 的形式，不要寫暗色字面 hex**——token 本身是亮/暗雙套，accent 指過去才會跟著主題走；細節與踩雷史見 §3.6）、`--accent-2`（進度條漸層尾色，同樣用 var()）、`--glow-1`／`--glow-2`（背景光暈，維持 rgba 字面值即可，alpha 極低兩主題通用）。
- **採用 .col-* 的頁**：mounts、emotes（置中）、barding、orchestrion、triple-triad、blue-magic。
- **保留專屬卡片、只共用外框的頁**：hairstyles（橫向卡）、minions（小方格＋tooltip）。
- 新增收藏頁：link common.css → 套 .col-* 卡片 → 設 4 個 accent 變數，專屬樣式才寫進該頁 `<style>`。

### 2.3 追蹤頁標配功能（2026-07 全面對齊，12 頁）
新頁請直接複製坐騎頁（`collections/mounts`）的這些區塊：
- **匯入**：驗 `data.schema`（各頁固定字串，如 `mounts-progress`、`minions_owned`），不符即拒絕；純陣列視為舊版備份仍接受；覆蓋前 confirm 顯示雙方筆數。
- **清除進度**：confirm 後先自動 `exportProgress()` 下載備份再清除。
- **批次標記**：工具列 `#markAllBtn`／`#unmarkAllBtn`，作用於 `filtered()` 結果，confirm 顯示筆數。
- **排序**：`.sort-select`（common.css）選單——預設／版本新→舊／版本舊→新／依名稱（zh-Hant localeCompare）。探索筆記無排序（id 順序即景觀編號）。
- **鍵盤**：卡片 `tabIndex=0` + `role=button` + `aria-pressed`，Enter/Space 切換；focus 樣式 `.col-card:focus-visible`。
- **首頁全站備份**：`#pdExportBtn`／`#pdImportBtn`，schema `seagod-toolbox-backup`，打包所有 `ffxiv_*` localStorage key；儀表板區塊永遠顯示（空狀態顯示 `#pdEmpty`）。
- 釣魚頁備份含 `owned`＋`targets`（schema `fishing-progress`）；採集紀錄 schema `gathering-log-progress`。
- **⚠ localStorage key 一律 `ffxiv_` 開頭**（工具頁也算，不只追蹤頁）——首頁備份是用前綴掃 key 的，
  取別的名字＝那頁的存檔**永遠不會被備份到，而且不會有任何提示**。
  小隊頁的 `squadron_v3` 就這樣漏了一年，07-29 才改成 `ffxiv_squadron`（含舊 key 一次性搬移）。
  幻化配裝圖鑑的 `ff14_favs` 也是同一個坑（併進來的子專案自帶的舊名），**08-28 已改成
  `ffxiv_favs`**——那之前使用者按首頁的「匯出全站進度」，幻化收藏整包沒被帶走且沒有提示。
  改既有頁的 key 時記得寫遷移：讀不到新 key 才回頭讀舊 key。**遷移期間舊 key 不要刪**——
  使用者可能還開著吃舊 SW 快取的分頁，刪了會兩邊互相蓋掉；`saveFavs()` 兩個 key 一起寫，
  等下次改版舊快取過期再拿掉。（市場頁 `tools/market/market.js` 的 `migrateLegacyKeys()`
  是現成範本。）
- **為何**：防止跨頁誤匯覆蓋與誤清除。

### 2.4 版本篩選統一格式「N.x 資料片繁中名」
2026-07-02 定案（commit bbcd9f1），取代先前混用的四種寫法。
- 六個資料片：**2.x 原初之地／3.x 蒼天之禁地／4.x 紅蓮之狂潮／5.x 暗影之逆焰／6.x 曉月之終途／7.x 金曦之遺輝**。
- 篩選控制項（chips/select）顯示一律「N.x 資料片名」（例 `3.x 蒼天之禁地`）；**資料值**保持資料片繁中名或 major 數字不變，只在顯示層加前綴（樂譜／藏寶圖以 `EXP_PREFIX` 對照表轉顯示）。
- 篩選邏輯以 major（`parseInt(patch,10)`）對應資料片，不逐小版本開 chip；篩選區標題統一「版本」。
- 卡片上的精確版本徽章（如 `3.35`）不受此規範。
- 已套用：mounts、hairstyles、orchestrion、exploration-log、treasure-maps（列標題）、weather（地圖群組）、fishing、gathering、gathering-log、aether-currents；寵物／幻卡／鳥鞍也已補上（PATCH_BANDS 模式同坐騎頁）。
- **例外：表情（emotes）刻意不提供版本篩選**（使用者要求）；blue-magic 目前無版本篩選，日後要加沿用本方案。

### 2.5 收藏頁共用引擎 `assets/js/collection-tracker.js`（2026-07-22 建立，07-23 擴充）
§2.3 的標配功能全部收進單一引擎，取代各頁 ~480–690 行的重複 JS。**全部 12 個追蹤頁**都已改為「header＋一份 `CollectionTracker.init({...})` 設定」：mounts／minions／barding／orchestrion／emotes／hairstyles／blue-magic／triple-triad（07-22）＋ exploration-log／aether-currents／gathering-log／fishing（07-23）。**不要再手寫追蹤頁的篩選／排序／渲染迴圈。**
- **引擎負責**：資料載入＋PatchGate 過濾、進度條＋`ffxiv_snap_<snapKey>` 首頁快照、工具列（搜尋／擁有切換／排序／批次標記／匯入匯出／清除）、標籤篩選區、格線渲染、鍵盤＋ARIA、以及 **URL 狀態同步**（`?q=&own=&sort=&f_<id>=`，打字 replaceState、離散操作 pushState、popstate 還原，可分享／加書籤）。控制面渲染進掛載點 `<div id="ct-root"></div>`。
- **各頁只提供設定**：`dataUrl／metaUrl／storageKey／snapKey`（＋可選 `schema／fileBase` 保留既有匯出檔相容）、`verb`（擁有/解鎖/習得）、`unit`（隻/個/張…）、`noun`；資料 hook `include(e,gp)／keyOf(e)／alwaysOwned(e)／searchText(e)／prepare(list)`；`filters:[{id,label,options(list),match(e,v)}｜{kind:'patch'}]`；`sorts:['name','patch-desc','patch-asc',{value,label,cmp}]`；`card(e)->innerHTML`；互動 hook `onCardClick(e,ev)`（回傳 true＝不切換擁有，如市場連結、幻卡 📍）、`onCardCreate(e,cardEl)`（掛額外互動，如寵物 hover 提示框）；版型 `gridClass／cardClass`（預設 col-grid/col-card；hairstyles=hs-*、minions=minion-*）。
- **搜尋預設涵蓋 `sources[].detail`**（可搜取得方式）；各頁可覆寫 `searchText` 加更多欄位（如幻卡加 npcName／mapName、青魔加習得地點）。
- **相容性鐵則**：`storageKey`／`schema`／`keyOf` 必須沿用各頁原值，否則洗掉使用者既有進度。特例：**minions 的 `keyOf` 回傳純數字 id**（既有存檔是 `[1,2,3]` 非 `['id:1']`）；emotes/hairstyles 等的 schema 沿用原字串。
- **驗證方式**：本機 headless Chromium 在此環境無法啟動（`chrome-headless-shell` 崩潰，exit 3221225786），改用 **jsdom**（暫存區裝，不進 package.json）載入引擎＋各頁真實設定＋mock fetch 讀真實資料檔做 DOM 層驗證。新增/改引擎後照此跑一次。
- **新增收藏頁**：複製任一遷移頁的 head＋設定即可；不要再回頭手寫 filter/sort/render 迴圈。

**三個選用能力（2026-07-23 新增，不設定即完全維持原行為）**
- **`subsOf(entry) -> [子項目]`「子項目模式」**：追蹤單位不是卡片本身而是卡片裡的東西時使用——風脈泉頁一張卡＝地區、要打勾的是 303 個風脈泉；採集紀錄頁一張卡＝採集點、要打勾的是產物。設定後 **`keyOf` 收到的是子項目**、進度分母＝子項目總數、卡片 `.owned` 代表「該卡子項目全數完成」、批次標記作用於篩選結果的所有子項目。**單位依 `keyOf` 去重**（同一件產物出現在多個採集點只算一件）。此模式下引擎**不綁卡片層級的點擊切換**，各頁在 `onCardCreate` 裡自己綁子項目並呼叫 `tracker.toggleKey(key)`。
- **`pageSize`（分頁）**：資料量大的頁面用（釣魚 60／採集點 40）。頁碼同步到網址 `?p=`（1-based，可分享），任何篩選／搜尋／排序變動自動回第 1 頁，頁碼超出範圍會夾回。樣式在 common.css 的 `.ct-pagination`／`.ct-page-btn`。
- **`onRender(list, pageSlice, tracker)`**：每次重畫格線後呼叫，讓各頁同步自己的附加檢視（地圖標點、目標魚面板）。
- **篩選 `render:'select'`（2026-07-26 新增）**：某組選項多到標籤排不下時改成下拉（釣魚頁的魚餌有 85 種）。搭配 `allLabel`（預設「全部」，value 為空字串）。網址同步、清除、還原全部沿用既有機制，不必另外處理。**下拉的 change handler 刻意不呼叫 `renderFilters()`**——下拉自己就顯示著目前值，重畫只會害使用者失去焦點；標籤路徑則仍要重畫才能更新 `.active`。

**其他選用設定**：`rowsOf(json)`（資料不在 `data[]` 時指定，風脈泉庫是 `zones[]`）、`defaultSort`（釣魚頁預設 `window`＝依開窗時間）、`exportExtra()`／`onImport(data)`（頁面自有的額外進度跟著匯出匯入走，如釣魚的目標魚清單）。匯入已改為同時接受 `owned`／`unlocked`／`done` 三種舊鍵名。

**踩過的雷**：卡片內若有自己的點擊行為（釣魚頁的 🎯目標／📍地圖／點圓圈勾已釣／點其他開詳情），**不要另外在 `#ct-root` 上做事件代理**——引擎已經綁了卡片層級的 toggle，兩邊都處理會變成「切換兩次＝沒切換」。正解是用 `onCardClick(e, ev)` 分流，回傳 `true` 表示「本頁已處理、不要切換」。

**踩過的雷之二（2026-07-25）**：**不要用 inline style 去藏 `#ct-grid`／`#ct-pagination`**。`renderGrid()` 每次重畫都會無條件把 `grid.style.display` 設回 `''`（只有清單為空時才設 `none`），而換篩選／勾選／匯入都會觸發重畫，所以 inline 的 `display:none` 會被安靜地洗掉。釣魚頁的「地圖檢視」就是這樣壞的——切過去後魚卡清單根本沒收起來，地圖被推到頁面 5700px 以下，等於找不到。正解是切 body class 配 `!important` 規則（現由 `map-explorer.js` 提供 `body.mx-mapmode`）。

### 2.6b 沒用引擎的頁面也要沿用共用樣式（2026-07-26）
不是每頁都適合遷入 `collection-tracker.js`——**限時採集節點查詢就不該遷**：引擎繞著「已擁有／進度」建（進度條、標記全部、匯出匯入進度、已/未三態），而那頁沒有「已採集」的概念，⭐ 是待辦清單＋鬧鐘；硬遷得在引擎加「無進度模式」，會波及 12 頁。**但「不用引擎」不等於「自己另一套版型」**。
- **檢查點：該頁有沒有載 `assets/css/common.css`。** 限時採集頁原本沒載，整套設計自己手寫、連 `:root` 色票都複製一份且已飄移（`--text-muted` `#4a5568` vs 共用 `#717c91`、`--transition` 0.2s vs 0.18s，另缺 `--cyan/--orange/--accent`）。使用者回報的「篩選方式跟其他頁面不同」，根因就是這個。
- **正解**：載入 `common.css`（放在頁內 `<style>` 之前，頁面專屬樣式仍然勝出），**刪掉重複的 `:root`**，然後直接用共用 class：`.toolbar`／`.search-wrap`／`.search-input`／`.sort-select`／`.icon-btn`／`.filter-section`／`.filter-label`／`.filter-tags`／`.filter-tag`／`.result-meta`。
- **版型與互動的統一規格**（新頁面照這個做）：上排 `.toolbar`（搜尋／下拉／開關），下方 `.filter-section` 分組標籤 chips。**篩選標籤每組單選、點已選中的等於取消**，所以**不要放「全部 XX」那顆**。布林開關（只看追蹤）用 `.icon-btn` 加自訂 `.on` 態，不要混進 `.filter-tag`。版本標籤一律「N.x 資料片繁中名」（見 §2.4）。

### 2.7 地圖檢視共用元件 `assets/js/map-explorer.js`（2026-07-25 建立）
釣魚／限時採集／採集紀錄三頁的「地圖檢視」共用同一支元件，版面沿用無人島採集地圖：**左底圖標點、右搜尋＋清單，兩邊連動**。取代原本三頁各自手寫的「一個下拉選單一次只能看一張地圖」。
- **用法**：`createMapExplorer({ mount, base, maps, unit, states, points, detail, ... })`，資料變動時呼叫 `.render()`。`points()` 回傳 `{ id, mapId, x, y, name, state, meta, live, search }`；`state` 對應 `states` 色表（同時決定圓點顏色與圖例），`live` 是會跳動的文字（倒數、已採 n/m）。
- **搜尋跨地圖**：地圖名／地區名／地點名／`search`（產物名、魚名）全吃；命中地圖名就整張留下，否則只留命中的地點，並自動跳到第一張有結果的地圖。
- **座標換算**：`pct = (c - 1) * sizeFactor / 41`，與 `map-modal.js`、無人島採集地圖同一條 FFXIV 標準式。底圖走 `image.local`，失敗改抓 `image.url`，再失敗才顯示「跑 `download-maps.mjs --id N` 可補齊」。
- **重畫分三層（限時採集每秒跑一次，不能整包重建）**：
  1. **結構簽章**＝「有哪些地圖、各有哪些地點」的**集合**（id 排過再串，**刻意與順序無關**）＋目前地圖＋選中項。變了才重建 DOM。
  2. **順序簽章**＝地圖順序＋目前這張圖的地點順序。變了只用 `appendChild` **搬既有節點**（詳情卡跟著它那一列一起搬），不重建 innerHTML，所以倒數、捲動位置、詳情卡都不會被打斷。
  3. **狀態顏色與 `live` 文字**每次都只做原地 patch；搜尋框永不重建，打字打到一半不會被洗掉。
- **`points()` 的順序＝頁面工具列選的排序，元件不再自己重排**（2026-07-26 修）。初版為了 DOM 穩定在三頁都寫死 `sort((a,b)=>a.id-b.id)`，結果**工具列的「排序」對地圖檢視完全沒作用**——現在改由上面的「順序簽章」處理，順序變動不會重建 DOM。**不要為了效能再把 id 排序加回去。**
  - 釣魚頁的釣場順序要**走 `filtered`（已排序的魚）逐條跑、釣場以第一次出現定序**，不能走 `SPOTS.values()`——後者是 id 序，一樣會蓋掉排序。兩種推導的釣場集合已比對過：**都是 307 筆、差集為空**。
- **地圖（群組）順序**＝該圖第一個地點在排序結果中的位置，所以換排序時左邊地圖與右邊清單一起動；唯一的強制規則是 `type=instance／dungeon` 殿後（見下條）。
- **詳情卡兩種更新法**，依內容選一種：只有倒數在跳 → 給 `tick(point, el)` 做原地更新（限時採集）；內容會因勾選而變 → 給 `detailSig(point)` 把它併進簽章，簽章一變就重建（釣魚的 ✓ 已釣、採集紀錄的 ✓ 已採）。兩個都不給則詳情卡只在結構變動時重建。
- **`body.mx-mapmode`**：規則放在 `assets/css/common.css`（不是元件裡），追蹤頁切到地圖檢視時 toggle 這個 class 即可（原因見 §2.5 踩過的雷之二）。**必須在 `<head>` 就載入**——採集紀錄頁的元件是動態 `import()`，規則若跟著元件才注入，開頁預設地圖檢視時清單會先閃一下。
- **每秒重畫的頁面，排序條件不可以沾到時間**（2026-07-26 教訓）。限時採集的預設排序原本是「版本 → 等級 → 開放狀態 → 倒數」，後兩項都是時間算出來的，於是清單每秒都在自己重排、節點開窗關窗還會整列跳位，連帶讓地圖清單也漂移（群組順序取自「該圖第一個地點在排序結果中的位置」）。**正解是排序只用靜態欄位（版本／等級／id），狀態改用顏色表達**——元件會把 `mx-s-<state>` 同時掛在圓點與清單列上，各頁自己上色即可。真的要「照倒數排」就做成使用者明確選擇的另一個排序選項，並在標籤上註明會隨時間重排。
- **地圖排序**：野外／主城在前，`type=instance／dungeon` 一律最後，各組內再依地點數多→少。**雲冠群島（The Diadem）就是靠這條排到最後**——它有 49 個採集點（全站最多）卻是要另外進本的特殊區域，排第一會擋住真正常用的野外圖。
- **三頁都預設開在地圖檢視**（2026-07-25 使用者指定）：`setView('map')`／`setGView('map')` 放在各頁 init 尾端。清單隨時可切回去，不記憶選擇（每次開頁都是地圖）。
- **三頁預設排序都是「版本新→舊」**（2026-07-26 使用者指定）：釣魚／採集紀錄用引擎的 `defaultSort: 'patch-desc'`，限時採集是自有下拉、預設 `sortMode = 'ver'`（版本新→舊＞等級，localStorage `gathering-sort-mode` 記使用者的選擇）。限時採集的 `ver` 在**版本與等級都相同時** tiebreaker 就是「開放狀態→倒數」，所以同版本同等級的地圖上 `ver` 與 `time` 順序會一樣——那是對的，不是排序沒生效。
- **sticky 位移**：地圖欄 `top:58px`（頂列 46px＋留白），與 aether-currents／treasure-maps 一致，見 §2.6。

### 2.8 ET 時鐘列共用元件 `assets/js/et-bar.js`（2026-07-26 建立）
釣魚紀錄追蹤／限時採集節點查詢／艾歐澤亞天氣預報三頁原本各寫一套時間顯示（釣魚是 hero 大字 `ET 20:26`、限時採集是左右兩塊 ET＋本地時間、天氣是含進度條的時鐘列），使用者反映「同一種資訊三種長相」。**現在統一由本元件產生，版型取天氣預報那一套。**
- **用法**：頁面放 `<div id="etBar"></div>`，`<head>` 加 `assets/css/et-bar.css`，然後 `mountEtBar('#etBar', { metric: 'weather' | 'ethour' })`。回傳 `{ el, update, stop }`，元件自己每秒 tick，**頁面不要再自建 `setInterval` 更新時鐘**。
- **三欄固定不變**：[艾歐澤亞時間＋日夜]／[週期標籤＋進度條＋倒數]／[現實時間＋「1 ET 小時 ≈ 2 分 55 秒」]。中欄的 `metric` 是唯一的頁面差異——天氣與釣魚用 `weather`（下次換天氣，8 ET 小時＝1400000ms），限時採集用 `ethour`（下個 ET 整點，175000ms），因為採集節點只吃 ET 整點、不吃天氣。**新增有時間的頁面一律用這支，不要再手寫時鐘。**
- **兩種週期的邊界都是 epoch 毫秒的整數倍**（1 ET 小時＝175000ms，天氣時段＝其 8 倍），所以進度直接用 `now % period` 算，不需要另一套 periodStart。
- **色票要帶 fallback**：`tools/weather` **沒有載 `common.css`**，只有自己的 `:root`（`--text-dim`，沒有 `--text-secondary`／`--text-muted`／`--radius-md`）。元件 CSS 因此一律寫 `var(--text-secondary, var(--text-dim, #8892a4))` 這種兩層退回；進度條軌道用中性灰 `rgba(127,127,127,.28)`（不吃 `--border`，否則在 common.css 系列的頁面是 `rgba(255,255,255,0.07)`，暗底上幾乎看不見）。**改元件樣式時記得三頁都要開來看。**
- **尺寸一律 px**：三頁的根字級不同（釣魚 `html{font-size:17.5px}`、天氣 `body{font-size:18px}`），用 rem 會讓「統一版型」在三頁長不一樣大。
- **驗收要開 HTTP**：三頁的主 script 都是 `type="module"`，`file://` 會被 CORS 擋掉整包 JS（畫面看起來像「元件沒掛上」）。用臨時靜態伺服器開 `http://localhost:<port>/tools/<頁>/index.html` 驗。

### 2.10 收藏切換一律是「卡片右上角的 ✓ 鈕」（2026-07-26 全站統一，使用者指定）
原本全站有四種長相：`.col-card.owned::before` 的 ✓ 角標（6 頁，不可點，靠點整張卡切換）、寵物圖示右下的 `.check-badge`、青魔法術書左上的金色方塊、幻卡右上的 ✓ 鈕。使用者要求「統一全網站的點擊收藏為右上角，並且要相同的格式」。

- **唯一定義處＝`common.css` 的 `.ct-check`＋`collection-tracker.js` 的 `buildCheck()`**。引擎替每張卡片加 `.ct-card` 並掛上這顆鈕（右上 6px、24px 圓形、未收藏 opacity .55、hover 1、已收藏填 `--accent`）。**各頁不准自刻**，自訂版型（青魔 `.bm-slot`、幻卡 `.tt-slot`）要收藏鈕就呼叫 `tracker.buildCheck(entry, owned, locked)` 並給格子加 `.ct-card`。
- **卡片本身不再切換擁有**（使用者選定）。誤觸是主因；卡片的點擊留給各頁的 `onCardClick`（看詳情、開地圖）。引擎因此不再對卡片設 `role=button`／`tabIndex`／`aria-pressed`，這些移到 ✓ 鈕上；`onCardClick` 的回傳值也不再有「true＝不要切換」的意義（照舊回傳無害）。要一次大量標記就用工具列的「✓ 標記全部／✗ 取消全部」。
- **`.ct-card:not(.ct-clickable) { cursor: default }`** 用 `:not()` 提特定度：各頁的 `.hs-card`／`.minion-card`／`.fish-card` 都寫在 common.css 之後且都有 `cursor:pointer`，同特定度會被蓋掉。
- **`alwaysOwned` 的項目（預設表情）給 disabled 的灰色實心 ✓**，不是不畫。不畫的話那 94 張卡看起來像壞的。
- **子項目模式（`subsOf`：風脈泉、採集紀錄）不掛這顆鈕**——那兩頁的收藏單位是卡片裡的 chip，卡片只是容器。
- **加了鈕就要替卡片右上角的內容讓位**：`common.css` 補 `.ct-card .col-name { padding-right: 26px }`（一次處理 6 個 `.col-*` 頁）、髮型 `.hs-info` 補 22px；**釣魚的 `.fish-patch` 版本號原本就絕對定位在 `top:.5rem right:.65rem`，正好被鈕蓋住，已往左讓到 `right:2.3rem`**。新頁若在卡片右上角放東西，記得先看有沒有撞到。
- **不做 `@media` 放大**：幻卡手帳手機版是 5 欄、格子約 58px，放大到 28px 會蓋掉半張卡面。24px 在最小的卡片（寵物頁手機版 92px）也按得到。
- **驗收方式**：`scratchpad` 的 `ct-serve.cjs`（`?ctprobe=1` 注入探針）＋ `ct-check.mjs`，用 headless Chrome 逐頁量「鈕是否真的在右上角、電腦樣式跨頁是否完全相同、點卡片不會改變收藏、點鈕才會、鈕有沒有壓到卡內文字」。**文字重疊要用 `Range.getBoundingClientRect()` 量墨水框**，元素 border-box 會誤報（`.col-name` 是 block，本來就橫跨整張卡）。12 頁 97 項全綠。

### 2.9 「仿遊戲內圖鑑」版型的做法（2026-07-26，青魔法術收藏首例）
使用者附遊戲截圖指定「用這樣的格式呈現，比較貼近遊戲」時的通用做法，實作範例＝[`collections/blue-magic/index.html`](../collections/blue-magic/index.html) 的「法術書」檢視（8 頁籤 × 4×4 格，仿〈青魔法之書〉）與 [`collections/triple-triad/index.html`](../collections/triple-triad/index.html) 的「手帳」檢視（15 頁籤 × 5×6 格，仿幻卡手帳）。**兩頁共用的骨架**：檢視切換鈕放 `#ct-root` 之前、狀態存 localStorage、body class 收合引擎格線、右側 sticky 詳情欄（`top:58px`）、底部「總計 n / m」、方向鍵可走到邊界自動翻頁。

- **格子位置必須固定**（青魔＝依 No.，每頁 16 格）。這個版型唯一的價值就是「跟遊戲裡看到的同一格」，可以照著對；**位置一浮動就沒有意義了**。
- **所以篩選／搜尋要「淡化」而不是抽走**（`.dim`，opacity .2）。引擎的 `filtered()` 回傳的是 `LIST` 內同一批物件，直接 `new Set(list)` 比參考即可判斷是否命中；另外在格線下方標「符合 n 個，其餘格子淡化顯示」，不然使用者會以為壞掉。整頁都沒命中的頁籤也一起淡化。
- **格子只建一次，之後只換 class**。引擎每次勾選都會 `renderGrid()` → `onRender()`，整片重建會吃掉鍵盤焦點、也讓 hover 斷掉。頁籤／總數／淡化狀態全部在同一個 `syncBook()` 內更新。
- **檢視狀態存 localStorage，不要塞網址**：引擎的 `buildQuery()` 每次互動都用自己的狀態重建整串 query，外掛的 `?view=` 會被安靜洗掉（同 §2.5 的 `#ct-grid` inline style 那個坑）。收合引擎自己的格線一樣要走 body class＋`!important`（本頁是 `body.bm-bookmode`），順便把「排序」下拉藏起來——固定排列的版型下它是無作用控制項。
- **未取得的格子用「原圖＋灰底」，不要用問號圖**（2026-07-26 使用者指定）。遊戲裡是灰底問號，但站上的頁還要負責「告訴你哪一招還沒學、去哪學」，全部變問號就得逐格 hover 才認得出來。已取得則是強調色底＋左上金色方標＋號碼轉強調色（對應遊戲格子左上的小方塊）。
- **詳情用固定欄位，不要用浮動提示框**：右側欄（≤860px 疊到下方）比 §2.6 的 hover 提示框適合這種密集格線——格子小、又要能點，浮動框會一直擋到隔壁格。寬螢幕（≥1160px）欄內再拆兩欄，否則右邊會留一大片空白。
- **選取靠「點」，不要靠 hover**（2026-07-26 使用者反映）：hover 切換詳情的話，滑鼠從中間的格子移出去會一路掃過旁邊好幾格，詳情跟著亂跳、等於選不到想看的那一個。**點格子＝檢視**（`.sel` 框標示目前檢視中），鍵盤 focus 也算（方向鍵是刻意動作）。
- **勾選要另外給一個明確的目標**：因為點格子被「檢視」佔走了。青魔是把遊戲格子左上的裝飾小方塊做成真的按鈕（未取得＝空框、已取得＝填金色），`stopPropagation` 不連帶觸發檢視；詳情欄裡另有一顆「標記為已習得」。**格子因此要用 `div[role=button][tabindex=0]` 而不是 `<button>`**——button 不能巢狀 button，改 div 後 Enter／空白鍵要自己補。
- **鍵盤**：方向鍵在整本書內移動並自動翻頁（左右 ±1、上下 ±欄數）。

**「淡化不抽走」有例外——圖多的頁改用引擎分頁（2026-07-26，幻卡手帳）**。上面那條的前提是格子很輕（青魔 124 個 40px 圖示）。幻卡一格是一張 208×256 的卡面（435 張約 6.7MB），全部畫出來只為了保住格位不划算，所以幻卡手帳改成：

- **直接吃引擎的 `pageSize: 30`**，手帳的「一頁」＝`onRender(list, pageSlice)` 給的 `pageSlice`。等於免費拿到：頁碼同步網址 `?p=`（可分享、popstate 可還原）、換篩選自動回第 1 頁、頁碼超界自動夾回，載入的圖也從 435 張降到 30 張。**篩選是抽走而不是淡化**，頁數跟著重算。
- 代價是「第 N 頁 ＝ 編號 (N-1)*30+1 起」只在未篩選時成立。可接受：頁籤旁常駐「第 n / m 頁」、底部「總計 n / m（篩選中；全部 X 張）」，狀態始終講得清楚。**排序下拉不藏**（此版型的頁組成本來就由引擎排序決定，藏了反而是失能）。
- 格子每次 `onRender` 重建（30 格很便宜），但**鍵盤事件與 focus 掛在格子容器**（`#ttSlots` `tabindex=0` `role=listbox`）而不是格子本身，所以重畫不會掉焦點；格子內的 ✓ 鈕 `tabindex=-1`，點完主動把焦點還給容器。
- **選中的那張永遠在當前頁**：`sync()` 發現 `selId` 不在 `pageSlice` 內就自動選這頁第一張，詳情欄不會空著（同遊戲）。
- **未取得的灰階不要在 hover／選中時也解除**：幻卡初版讓選中的格子透出原色，結果「選中的未取得卡」看起來就像已取得。現在只有 hover 微透（transient），選中只加框。
- 兩處以上會用到的格式化（四向數值十字、來源說明行、📍 開地圖鈕）抽成頁內的 `TTFmt`，不要各寫一份。

**仿遊戲版型的第一件事：確認遊戲的排列規則，不要假設是編號**（2026-07-26 幻卡教訓）。幻卡手帳的順序是 `TripleTriadCardResident` 的 **先 `UIPriority` 再 `Order`**，不是編號：15 張 FF 歷代主角卡（編號 68–80、252 諾克提斯、405 克萊夫，`UIPriority=5`／`SortKey=48`）被遊戲整批排到最後一頁，其後每張普通卡的位置都比編號小 13。使用者是直接對照遊戲畫面發現的（「有 15 張放在最後一頁，並沒有在對應的編號內」）。做這種版型時**先去 sheet 找排序欄位**（`Order`／`SortKey`／`UIPriority`）並存進資料，前端照它排；順手在詳情欄標「手帳第 N 頁」，使用者才能拿站上的結果回遊戲裡翻。
**編號也要照遊戲的規則，不是資料的 row id**（2026-07-26 幻卡定案）。幻卡畫面上的「編號」＝`Order`：420 張一般卡是 1–420，15 張主角卡在遊戲裡不在編號序列內 → 站上標「**編號外 1–15**」（卡格左下角縮寫「外1」）。row id 只留作**進度存檔的鍵**（`keyOf` 不能動，否則洗掉使用者進度），不對使用者顯示。副作用要一起想到：Shadow Lord 從 435 變 420、420÷30 剛好整頁，所以最後一頁整頁都是編號外那 15 張。

**仿遊戲的換頁列不要照抄遊戲的「一次跳一組」**（2026-07-26 使用者回報「換頁的功能很難使用」）。初版做成 `« 1 2 3 4 5 »`、`«/»` 一次跳 5 頁一組（遊戲就是這樣），結果要到第 12 頁得先按兩次 `»` 再點 12。**正解：頁數不多（≤20）就把所有頁碼一次列出來一鍵直達，再加「‹ 上一頁／下一頁 ›」走單頁**，並讓頁碼列 `position:sticky; top:46px`（頂列高度）——一頁 30 格有 6 排、將近 1500px 高，捲到底還要滑回頂端換頁本身就是坑。頁數真的多才退回「首末＋當前±3＋…」視窗式。**版型可以仿遊戲，操作效率不要跟著仿。**
**做完之後使用者可能要求「不要分兩種檢視」（2026-07-26 幻卡）**。幻卡最後**整頁只留手帳**，原本的 `.col-card` 清單與切換鈕全部移除。做法：引擎照舊 init（進度／工具列／篩選／排序／分頁狀態都還要它），但 `card()` 直接回傳空字串、`#ct-grid`／`#ct-pagination`／`#ct-empty` 用 `!important` 收起（同 §2.5 的雷之二，**不能用 inline style**）。空結果與分頁改由自訂版型自己顯示。青魔則仍保留兩種檢視——這是逐頁的使用者決定，不要自己統一。

### 3.3 時間一律 24 小時制（2026-07-24 定案）
ET 時窗、天氣時段、現實時刻，**顯示與儲存全部用 24 小時制**（`ET 09:00–12:00`、`7/25 14:26`），不用 am/pm。

**Why**：`12am`／`12pm` 誰是午夜誰是中午極易看錯。無人島動物的外部來源就栽在這裡——原文寫
`9am-12am`（字面是 09:00→00:00、15 小時），實為 `09:00-12:00`。是「全表時窗皆 3 小時」這個結構性
特徵才把它抓出來的，光看字面看不出錯。

**How to apply**：
- 資料檔存 0–23 的整點，時窗用半開區間 `[start, end)`。
- 外部來源寫 am/pm 時**先換算再填**，不要把 am/pm 原樣留在資料裡。
- 能加護欄就加：`build-island.mjs` 會驗 `animalSpawns.start/end` 必須是 0–23 整數、必須成對、不得相等，
  寫成 `"9am"`／`9.5`／`25` 都會 throw 並指出是哪一筆。**資料檔寫錯就炸**這種護欄比文件約定可靠得多
  （天氣名也是同樣做法，見 §5.9b）。

### 3.4 窄螢幕的格線一律要能縮到 min-content 以下（2026-07-28 修）

`common.css` 有一條 **`.col-grid > * { min-width: 0; }`**，不要拿掉。

**Why**：`grid-template-columns: 1fr 1fr` 的軌道下限**不是 0，是項目的 min-content**。
各頁在窄螢幕寫死兩欄、三欄時，卡片內容撐不下就會把軌道撐大，整頁橫向溢出。
坐騎頁在 430px 實測：`.col-grid` 容器只有 367px，軌道卻算成 `198px 198px`（198×2＋10 gap＝406），
**整頁溢出 15px**——剛好等於捲軸寬，很容易誤判成 `100vw` 的問題（它不是）。

**How to apply**：新頁若自訂 `grid-template-columns`，寫 `minmax(0, 1fr)` 或確保吃得到上面那條規則。
`repeat(auto-fill, minmax(200px, 1fr))` 這種**有明確下限**的寫法不受影響。

### 3.5 本機的瀏覽器量測：headless **Edge** ＋ CDP（不必裝 puppeteer）

本機 headless Chromium 起不來（`chrome-headless-shell` 崩潰），但
`C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe` 可以，而且 **Node 24 有原生 `WebSocket`**，
所以直接講 CDP 就行，不需要 puppeteer／playwright（專案也沒裝）。做法：
起一個 node 靜態伺服器 → `spawn(EDGE, ['--headless=new', '--remote-debugging-port=P', ...])` →
`fetch('http://127.0.0.1:P/json/list')` 拿 target → `new WebSocket(target.webSocketDebuggerUrl)`。

兩個踩過的雷：
- **`Emulation.setDeviceMetricsOverride` 要用 `mobile: false`**。設 `true` 會讓頁面退回 980px 的佈局寬，
  量到的根本不是你指定的寬度（會看到「視窗 980」這種明顯不對的數字）。
- **Git Bash 會把 `/collections/mounts/` 轉成 Windows 路徑**，傳頁面路徑當參數時要
  `MSYS_NO_PATHCONV=1`，否則會看到 `C:/Program Files/Git/collections/mounts/`。

適用場景：水平溢出（`documentElement.scrollWidth` vs `clientWidth` 並列出超界元素）、
console error 總檢、實際點擊互動驗收。jsdom 只驗得了 DOM 結構，量不了版面。

### 3.6 設計 token 單一來源 `assets/css/tokens.css`（2026-08-01 建立）

**Why**：此前 26 頁各自在 `<style>` 內複製一份 `:root` 色票，共 4 套以上副本，值已漂移——
`--bg-card` 有 `#14181f`／`#12161e`、`--border` 有 3 種寫法、**內文色有 `#e8eaf0`／`#e8e3d8`／`#d4cfc7` 三種**
（跨頁瀏覽時正文顏色會變）、`--radius` 8px vs `--radius-md` 10px、`--transition` 0.18s vs 0.2s。
而且並存兩套命名（`--text-primary/-secondary/-muted` 與 `--text/--text-dim/--text-muted`），
theme.css 只好「兩套都覆蓋」硬扛。

**How to apply**：

- 暗色基準一律寫進 `assets/css/tokens.css`，亮色覆蓋一律寫進 `theme.css`。**新頁不要自己開 `:root` 色票**，
  只設本頁的 `--accent`／`--accent-2`／`--glow-*`。
- 舊命名（`--text`／`--text-dim`／`--muted`／`--radius`／`--bg`／`--card-bg`／`--panel-bg`／
  `--amber`／`--ok`／`--warn`／`--danger`／`--isl-*`／`--female`…）在 tokens.css 內以 `var()` 定義成別名，
  舊頁的 CSS 規則不必逐條改寫。**別名不要在 theme.css 再覆寫一次**，否則別名會斷開、又長回一份平行色票。
- 字體也走 token：`--font-sans`／`--font-mono`。先前三套堆疊並存，其中 `'Segoe UI', system-ui, sans-serif`
  （5 頁）**缺 `Noto Sans TC`**，繁中字會 fallback 到不同字體。
- 新增 tokens.css 這類全站共用檔時，**`sw.js` 的 `PRECACHE` 要一起補**（`bump-sw-version.mjs` 只算雜湊，
  不會幫你加進預快取清單）。

**踩過的雷：`--accent` 在亮色模式全站洩漏。**
theme.css 曾有一組 `--accent:#2f6fb0`，註解寫「weather 專用」，但它掛在 `:root[data-theme="light"]`——
那是**全域**選擇器，特定度 (0,2,0) 高過各頁 `:root` (0,1,0)，結果把 13 個頁面各自的識別色
（金／紫／紅／綠／橘／藍）在亮色模式下全部壓成同一個藍，頁面識別完全消失。
正解有兩層：① 各頁 `--accent` 寫成 `var(--gold)` 這種指向 token 的形式，自動跟著主題走；
② 真的要自訂的頁（weather、fashion-report）在**自己的 `<style>`** 內寫 `:root[data-theme="light"]{--accent:…}`，
靠「同特定度、後載入」勝出，不會外溢。**別再把單頁的顏色寫進 theme.css。**

### 3.7 全站無障礙基準（2026-08-01 定案，規則在 tokens.css）

- **焦點環**：tokens.css 有一條 `:is(a,button,input,select,textarea,summary,[tabindex],[role=button]):focus-visible`，
  特定度 (0,2,0)，蓋得過各頁 `input{outline:none}` 一類 (0,1,0)～(0,1,1) 的寫法，所以舊頁不必逐條刪 `outline:none`。
  **但同為 (0,2,0) 又後載入的規則會贏**——已修的兩處：common.css 的 `.sort-select:hover,.sort-select:focus{outline:none}`、
  glamour 的 Bootstrap `.btn:focus-visible{outline:0}`（該頁補了一條同名規則蓋回去）。
  改共用 CSS 時若要寫 `outline:none`，先想清楚特定度。
- **`prefers-reduced-motion`**：tokens.css 統一處理（關掉 smooth scroll 與所有 transition/animation）。
  本站動效都是裝飾性，全關不影響功能。各頁不必自己寫。
- 驗收方式：用 §3.5 的 headless Edge ＋ CDP `Input.dispatchKeyEvent` 連按 Tab，
  逐一讀 `document.activeElement` 的 `outlineWidth`／`outlineStyle`；減少動態用 `Emulation.setEmulatedMedia`。
  已驗過 9 頁 × 22 個 tab stop 全數有環。
- **跳至主要內容**：`.sgt-skip` 樣式在 tokens.css、由 nav.js 注入在頂列**之前**（要當第一個 tab stop）。
  目標依序取「`.tool-header` 的下一個兄弟 → `main` → `.main` → `.container` → `.wrap`」。
  ⚠ `querySelector('main, .main, .container')` 這種寫法是**文件順序最前者勝**，不是清單順序勝——
  收藏頁的 `.container` 包著 `.tool-header`，寫成一串會選到 `.container`，等於只跳過頂列。要逐項自己試。

### 3.8 對比：問題幾乎都出在「同色文字疊同色淡底」（2026-08-03 全站掃描定案）

用 headless Edge 掃 26 頁 × 亮/暗兩主題，量到 **168 類文字未達 WCAG AA**。修完後兩個主題都是 0。
歸納出三條會重複踩的：

1. **算對比要把半透明背景沿祖先鏈合成**。`background: var(--x-dim)` 是 `rgba(...,0.1)`，
   直接拿它的 RGB 去算會得到「同色配同色＝1.0」這種假數字；也不能只看元素自己的 `backgroundColor`
   （多半是 transparent）。正確做法：從 `html` 的底色往內逐層 `over()` 合成，文字色若也半透明要一起合成。
   量測腳本留在 scratchpad，改配色後照跑一次。
2. **各頁自己刻的標籤幾乎都寫死暗色字面值**（`#4ade80`／`#ffa94d`／`#fbbf24`…）。
   亮色模式沒有對應覆蓋 → 淺綠字配淺綠底，實測只有 1.6–2.5:1，等於看不見。
   已全部改指 token（`--green`／`--green-dim`…）。**新標籤一律用 token，不要寫十六進位。**
   同理 JS 裡的顏色常數也要（天書的 `barColors` 就是寫死暗色，亮色下 1.67:1）。
3. **「色 vs 純白」過關 ≠「色 vs 同色淡底」過關**。`-dim` 疊上白卡後底色 L≈0.85，
   同一組色會掉 0.5–0.7。全站的 active 狀態（`.filter-tag.active`、`.tab.active`、`.own-btn.active`、
   `.chip`、`src-tag`…）走的都是這個組合。已把亮色 `-dim` 的 alpha 統一降到 0.10、
   文字色各加深一級；`--gold` 亮色由 `#8a6c2f` → `#755a26`。**調亮色色票時要拿 -dim 當背景驗，不是拿白色。**

另外兩個獨立的坑：
- **實心底標籤的文字色不要寫 `#fff`**。底色是 token（亮/暗兩套）而文字寫死白色時，只有一個主題成立
  （glamour 的篩選鈕在暗色是 3.85）。用 `var(--bg-base)`——底亮字就深、底深字就亮，兩邊都對。
  站內既有範例：common.css 的 `.ct-card.owned > .ct-check`。
- **Bootstrap 的預設語意色不吃站內 token**（glamour）。`.btn-outline-secondary` 的灰在本站深底只有 2.0:1、
  `.text-secondary` 3.79。改法是導 `--bs-btn-*` / `--bs-secondary-color` 到站內 token，不必改 HTML class。

### 3.9 觸控目標：用 `pointer: coarse`，而且只設 `min-height`（2026-08-03）

375px 實測全站手指要點的東西幾乎都在 12–40px：`.filter-tag` 31px（**每頁最主要的操作，一頁 20–40 顆**）、
`.ct-check` 24px（12 個追蹤頁**唯一**的標記入口）、`.ct-page-btn` 29px、軍票頁的核取方塊 13px。

- **條件用 `@media (pointer: coarse)` 不用 `max-width`**。這是「手指粗細」不是「螢幕寬度」的問題；
  用寬度會漏掉橫放平板／觸控筆電，又會在窄視窗的桌機上把密集版面撐開。桌機滑鼠完全不套用。
- **只設 `min-height: var(--tap-min)`（44px），不動寬度**。垂直長高不會撐破橫向密集的工具列／頁籤列；
  寬度硬撐會直接破版。所以量測結果裡還會看到「寬度 28–41px」的窄鈕，那是刻意的。
- **不能長高的（格線的格子、絕對定位的鈕）改用透明 `::after` 擴張命中區**，視覺尺寸不變：
  `.ct-check::after{position:absolute;inset:-10px}` → 看起來仍是 24px、手指按得到 44px。
  幻卡手帳（手機 5 欄、格約 58px）與青魔法之書收斂成 `inset:-6px`，不然會蓋掉「點格子看詳情」。
- 保底規則在 tokens.css（`button`/`select`/`input`/`summary`/`[role=button]`），
  例外清單 `.ct-check, .tt-slot, .bm-slot, .col-card, .cell` 設回 `min-height:0`。

### 3.12 階層資料不要攤平成清單——要「縮排＋可勾＋同層合併」（2026-08-09，市場查價的教訓）

`tools/market/` 的採買清單改過兩版才對。**攤平是錯的起點**，記下來免得下次又走一遍：

**(a) 攤平會讓「中間物」整個消失，使用者連話都沒地方講。**
最省樹上每個節點各自比買／做，把 `mode==='buy'` 的節點攤平成一張表後：① 第 1 層原料與第 3 層原料並排，看不出誰是誰的材料；② **計畫中「要自己做」的中間物根本不在表上**（它不是 buy 節點），於是「我已經有第一層材料了」無處可表達，使用者只能被迫去勾用不到的第二層材料。
先試過「依層級分組」——**解決不了**，因為問題不是排序，是那一列不存在。
✅ 正解：**保留樹的形狀**。一列一節點、縮排＋導引線表示上下層、每列都能勾「已有」。
查 `ui-ux-pro-max` 的依據：階層 >3 層時 treemap／sunburst 都不適用（無障礙僅 C 級），主檢視應是 collapsible tree table；最接近的 Decomposition Tree 是唯一 AA 級（縮排＋展開收合＋鍵盤可操作）。`visual-hierarchy` 另明講層級要靠**縮排與間距**，不能只靠顏色。

**(b) 勾選要能改變計畫，不能只是打勾。**
「已有」若只是畫刪節線，使用者還是得處理底下的材料。做成規劃的輸入：最佳化函式吃一個存量 pool，逐節點先扣已有，需求歸零就收斂成 `have` 且**不再展開子樹**。
⚠ 兩個踩過的坑：① 子節點必須在 pool 的**複本**上試算——決定「直購」時整個子樹會被丟棄，直接在本體上扣會把存量憑空吃掉，只有真的採自製才寫回。② 「✓ 我有了」要用**全計畫合計需求**一次補滿所有分支，不是只補當前這一列，否則同一種料被兩個成品用到時永遠補不滿。

**(c) 同一層的相同物品一定要合併，否則看不出總數。**
一種料被兩個成品（或兩個中間物）用到會拆成兩列各報各的數。逐層按 id 合併，數量相加、副標列出所有上游。順帶也收斂了「同一份配方把同一種料寫在多個材料欄」（配方資料真的有，例：41810 有 4 欄木棉木材）。
**跨層合併不了**（會破壞樹的形狀），所以那一列要加註「全計畫共需 N（另 M 個在其他層）」，並另外提供一個全域合併的採買彙總。

**(d) 目標物本身不是「材料」，不要放進備料清單——但它的配方還是要展開。**
清單從各目標物的**下一層**開始。⚠ 這一層不可以用「計畫用的下層」：目標物一旦被判定「直接買比較便宜」，計畫下層就是空的，**整份配方都不會進清單**，使用者加了那種東西進清單會完全看不出畫面有變化（實測列數 20 → 20，只有旁邊的顆數與採買彙總有動）。要用「畫面可展開的下層」，並把它們標成非計畫項。

**(e) 「不列入計算」≠「不給看」，而且不要因此在畫面上另眼相待。**
判定「直接買」的節點，它的材料**不能算進項數／金額／採買彙總**（買了上層就用不到），但**還是要能展開來看**——使用者手上可能就有那些料，標記已有之後自製成本會下降，那一層就會自己從「買」翻成「做」。做法是把「計畫用的下層」與「畫面可展開的下層」拆成兩個函式（`activeChildren` / `displayChildren`）。
⚠ **算不算進總數是內部帳，不該外顯成不同的長相**。這一版試過「淡化＋註記『參考：上層改成買了就不用備』」，被打回；最後定案是**買與做完全同一種顯示方式**：都可展開、預設都展開、單價／小計兩邊都填（做＝自製單位成本與材料總成本）、副標同一句型只是方向相反，差異只剩徽章。（也見 §1.6）

**(f) 階層與攤平要兩種都給，而且「這是什麼東西」要用底色講。**
階層看得出誰是誰的材料，卻要跨層心算總數；攤平看得到總數卻看不出關係——**只給一種一定不夠用**。做成可切換的檢視（本站五種：階層／直接材料／全部素材／基礎素材／中間物，選擇記進 localStorage）。
三個細節：
① **跨層合併只有在攤平檢視做得到**（樹的形狀不允許），所以「某某總共要幾個」的正解在「全部素材」那一檢視。
② **攤平檢視不可以套用「計畫」的過濾**。第一版拿 `activeChildren`（買到就停）去攤平，結果叫「全部素材」的檢視比「階層」還少——實測階層 16 項、全部素材只剩 7 項。攤平回答的是「這份配方由什麼組成」，跟買／做的建議是兩回事，要走 `displayChildren`。**驗收方式：全展開的階層列集合，必須等於「全部素材」的列集合。**
③ **合計列只在「列與列不會互相包含」時給**。直接材料（全是兄弟）、基礎素材（全是葉子）可以加總；全部素材（含中間物與它的材料）與中間物（中間物本身也會互相巢套，例氧化鎂砥石在黑星石底下）都會重複計算，不給。
另外「**是不是自己做得出來**」要用底色直接講（綠底＝中間素材、無底色＝基礎素材），它和「買／做的建議」是**兩個不同的軸**——一個中間素材完全可能因為市價便宜而被建議用買的。

**(g) 「全部展開」不能只套用在畫面上現有的列。**
收合狀態下深層的列根本還沒渲染、路徑不存在，用「當下渲染出的路徑集合」去設狀態，按一次只會展開一層。要用一個全域旗標，優先序＝個別點過的覆寫 > 全部展開／收合 > 各節點的預設。

### 3.13 「買不到」有兩種語意，別混講；彙總樹時也別在無解節點整支 return（2026-08-09，市場查價的教訓）

兩條都出自 `tools/market/`，但適用於任何「把樹狀最佳解攤平成清單」或「顯示市價」的頁面。

**(a) 遞迴彙總遇到無解節點，不能 `return`。**
原本 `collectShopping()` 寫成 `if (n.mode === 'na') return;`——只要子樹裡有**一件**買不到的材料，該節點就被判 `na`，**整棵子樹的採買列會靜靜整批消失**，畫面上完全沒有跡象（總成本欄只會淡淡寫一句「部分材料無市場資料」）。實例：「熱帶風情四柱床」只因缺一項「香木屑」，底下 8 筆買得到的材料全部不出現。
✅ 正解：**無解但還有下層 → 繼續往下走**（底下取得得到的照列）；**真正的葉子死路 → 收進獨立分段明講**。「算不出總價」和「這些東西不用列」是兩件事。

**(b) `marketable === false` 與「此查價範圍剛好沒人在架」不是同一件事。**
兩者在程式裡都表現為「拿不到單價」，但給玩家的行動完全相反：前者要去採集／打副本／兌換，後者只要換個查價範圍或等一下再看。混成一組會把「等一下再看」錯講成「去採集」——**單服模式、冷門素材、Universalis 暫時無資料時整批都會中招**（實測用一個不存在的 world id，全部 4 筆都被標成「需自行取得」）。
✅ 分開講：`!marketable` →「不可交易 · 需自行取得」；`marketable` 但無在架 →「<查價範圍>查無在架 · 換個範圍或稍後再試」。
順帶：**全部查無市價時金額加總會是 0**，直接印「剩餘採買 0 G」會被讀成「不用花錢」，要改印「無市價」。

**(c) 表格分組的寫法**（同批一起定的，之後有分層表照抄）：一段一個 `<tbody>`，段首用 `<th colspan scope="colgroup">`（不是 `<td>`，讀屏才會把底下的列當同一組報讀）；多欄表包一層 `overflow-x:auto` **並且要給 table `min-width`**——沒有 min-width 的話 table 會硬縮欄寬把中文壓成一字一行，wrapper 反而永遠捲不動。

### 3.14 市價成本＝逐筆吃掉掛單，不是「最低價 × 數量」（2026-08-10，市場查價的教訓）

**這是本站曾經最嚴重的一個算錯。** `tools/market/` 原本用
`unitBuy(id) * need` 算採購成本——取市場板最低那一筆的單價，乘以需求量。

問題：**最便宜那一筆常常只有 1～3 個**。實測「木棉木長槍」要買 100 個，
最低價 15,000 G，舊算法報 1,500,000 G；逐筆吃掉掛單的真實成本是
**1,874,770 G（均價 18,748）**，而且整個陸行鳥 DC 只湊得到 11 個。
低估幅度**隨數量放大**，而它正好是「買 vs 自製」判斷的關鍵輸入——
量越大越容易誤判成「買比較划算」。

✅ 正解＝`assets/js/universalis.js` 的 `fillQuote(itemData, need, {hq, cap})`：
把該品質的掛單依單價升冪排好，逐筆吃到滿為止，回傳總價、加權均價、
吃到的掛單明細（含各筆的伺服器）。**任何「買 N 個多少錢」都走它。**

連帶必須處理的四件事（不做的話數字對了、話講錯了）：

- **listings 取樣數要夠**。原本只跟 API 要 8 筆，對上百個的需求根本不夠。
  現在要 30（`LISTINGS_CAP`）。
- **「湊不滿」有兩種，處置完全不同**：`短缺`＝整個範圍真的沒那麼多貨（要換範圍／等補貨）；
  `超出取樣`＝回應被 listings 上限截斷，看不到的掛單不算不足（只是估算會不準）。
  用「回傳筆數是否等於 cap」區分，混講會嚇到使用者。
- **HQ/NQ 是偏好不是硬條件**。想要的品質沒在架時退回另一種是對的，但**不能靜默**——
  舊版 `p.hq != null` 直接退回 NQ，畫面上完全看不出來。要回報 `hqFallback` 並明講。
- **一筆需求可能橫跨多個伺服器**。採買彙總依伺服器分組時要走 `quote.lines` 逐筆掛單拆，
  不能拿「最便宜那筆所在的伺服器」代表整批——那會叫人在只有 3 個貨的地方買 100 個。

**衍生的兩個顯示慣例**：
- 「最低價那筆只有 N 個」要標出來（誘餌單）。加權均價比最低價高一截時，
  使用者會拿畫面數字去對市場板首頁的最低價，對不上就會覺得工具算錯。
- 逐物品標**資料新鮮度**（listings 各自帶 `lastUploadTime`）。整頁只印一個
  「最後更新」會讓冷門素材的三週前舊價，跟熱門素材長得一模一樣。

**全 DC 最低價有隱藏成本**：它是「每項各自的最低價」，那些最低價散在 8 個服。
為省 2,000 G 跑三個伺服器並不划算，但畫面從來沒提過。現在加了「一站購足」比較——
**每個世界要各查一次價，不能拿 DC 前 30 筆去篩世界**（DC 前 30 筆裡可能只有 2 筆
屬於泰坦，但泰坦自己可能還有 28 筆沒被取樣到，篩出來會假性偏貴）。8 次請求，
只在使用者按按鈕時跑。

**效能**：把「查價」與「計算」拆開（`priceStore` 依 scope 快取逐物品掛單，
`quoteCache` 快取算好的報價）。勾一列「我已經有了」只改計算前提，實測
**新增 Universalis 請求數 0**。

### 3.16 買與賣是兩個不同的範圍；交易稅買賣兩邊都抽（2026-08-10，市場查價的教訓）

**FF14 市場板的兩條規則，前端一定要分開處理：**

| | 範圍 | 稅 |
|---|---|---|
| **買** | 可跨伺服器（世界訪問） | 在成交價**之上額外付 5%** 手續費 |
| **賣** | **只能在自己角色所在的伺服器**掛售 | 成交價**之中被扣 5%** 交易稅 |

踩過的兩個錯：

**(a) 售價用了全 DC 最低價。** 賺錢排行原本買賣共用同一個 scope（全 DC），
結果拿「別的伺服器的最低價」當你的售價——**那個價你根本掛不上去**。
正解是兩次查詢：售價與日銷量走 `homeWorld`，材料成本走全 DC。

**(b) 稅算成只有賣方負擔。** 買賣兩邊都抽，方向或邊數弄錯，
成本少算 5% ＋ 收入多扣 5%，**利潤整整偏掉一成**。

連帶的兩個設計決定：

- **「買東西的範圍」不該做成選單**。買本來就能跨服，讓使用者選只是逼他做一個
  沒有意義的決定（選單服只會看到比較貴或根本沒貨的結果）。留一個「我的伺服器」就好。
- **限定自家伺服器後，很多成品在那一服根本沒人在架**。早期版本直接跳過那些
  項目，整張表變空（實測 100 項只剩 0 項）。**沒人在架不是「沒有價值」而是
  「沒有競爭者」**，是這功能最該告訴你的情況之一——退用該服近期成交均價估，
  並標示「無競爭者」。
- 顯示上把「單價（未稅，對得上遊戲畫面）」與「小計（含稅，實際付出）」分開標，
  像購物車一樣：品項標價未稅、結帳金額含稅。

（已知但刻意不做進 UI：雇員登記數少的市場有 2%／5% 限時減稅活動，
幅度與期限只在遊戲內看得到，外部 API 拿不到，做成介面只會是個永遠不準的欄位。）

### 3.18 折疊要讓「摘要行本身就是資訊」；徽章成串要用 flex gap（2026-08-10）

**(a) 資訊過載的解法不是「藏起來」。** 市場查價的單品面板一度把走勢／試算／
自訂價／利潤／取得管道／在架明細／上下游配方全部攤開，一個物品要捲三四個螢幕。
單純折疊只是換個地方塞——使用者還是得一個個點開找。

✅ 正解：**收合狀態的摘要行就要帶出結論**，多數情況看摘要就夠：

| 區塊 | 摘要行 |
|------|--------|
| 📈 價格走勢 | 近 30 日第 9 百分位（偏低） |
| 💰 製作利潤 | ▲ ＋12,468 G / 1 個 |
| 📋 在架明細 | 30 筆 NQ 在架 |
| 🔗 上下游配方 | 材料 2 種 · 用於 79 項 |

配套的兩件事：**展開狀態要持久化**（習慣看在架明細的人展開一次就一直開著），
以及**先刪再折**——數字卡先從 5 張砍到 3 張（NQ／HQ 兩張最低價卡與下方的
NQ/HQ 切換講的是同一件事），折疊才有意義。實測面板高度多螢幕 → 616px。

⚠ **`<details>` 的 `toggle` 事件不會冒泡**，不能用事件委派，只能逐個掛監聽；
面板若分兩段渲染（骨架立刻、資料等 API 回來），兩處都要掛，並用
`dataset` 旗標防重複綁定。

**(b) 徽章成串一律用 flex gap，不要各自設 margin。** 各處自己用 2～3px margin
排徽章，兩三枚並排會糊成一塊，看不出是幾個標籤（實測「遠航探索寶箱/容器分解獲得」）。
統一包一層 `.flag-run { display:inline-flex; flex-wrap:wrap; gap:6px }`，
6px 與篩選列 chip 的「群組內」基準一致（見 §3.15）。

**(c) 說明文字：三種一律砍掉。** 折疊之後才發現真正的問題是**話太多**。
盤點全頁後，這三類一律刪：

1. **UI 自己已經說明白的**。「我實際買到的單價」＋數字框旁邊，再補一句
   「填了之後製作清單一律用這個價算，不再看市價」——標籤已經講完了。
   同理「成品卡上的『自動／NQ／HQ』可逐件覆寫」——那組鈕就在畫面上，看得到就會按。
2. **在解釋我們資料管線的限制**。「遊戲資料只記錄了『有這條管道』，沒有具體地點或對象」
   ——那是給維護者看的，該進程式註解。使用者只需要知道「有這條管道」。
   同理「水晶為基礎素材，不列出上下游配方」：整區不出現即可，不必印一行字解釋為什麼不出現。
3. **教學式散文**。「日均可賺＝單件淨利 × 市場日成交量，假設成交量全被你吃下——
   實際會被別的製作者分掉，它的用途是把…放在同一把尺上比」→ 搬進表頭的 `title`
   （想知道才滑過去看）。**計算方法的說明放 tooltip 與文件，不佔畫面。**

留下來的只有兩種：**會改變行動的警告**（缺報價、未設伺服器、取樣被截斷）與
**空狀態的下一步**（UX `empty-states` 準則）。實測單品面板的說明文字從數百字
降到只剩「加入製作清單：」7 個字。

順帶：**窄的數字框不要放中文 placeholder**，會被截成「留空＝用市」；改用 `title`。

**(d) 同一種東西只准有一套樣式。** 「連在一起」除了徽章，還有折疊列自己：
`.fold` 原本只有 6px margin ＋ 淡邊框，四張並排看起來像一整塊表格（改 10px）。
更關鍵的是「取得管道」當初自己刻了一份 `.src-box`——不同底色、不同內距、
不同摘要結構，夾在一串 `.fold` 中間像誤植的另一種元件。
**發現自己在為某個區塊「再刻一套外框」時，先問能不能用既有的那套。**
併回共用的 `foldHtml` 之後，六個區塊同類別、同底色、同內距、同間距、
同一套展開狀態持久化。

### 3.15 篩選列：所有間距一樣＝沒有分組（2026-08-10）

`tools/market/` 的篩選列原本是「十個職業 chip ＋『等級』標籤 ＋ 兩個輸入框」
全部 `gap: 6px` 平均排開。看起來很整齊，但**讀不出哪幾個是一組**——
使用者得逐個看文字才知道「等級」管的是右邊那兩格、不是左邊那排 chip。

✅ 兩級節奏（4/8 為基準單位）：

| 層級 | 間距 | 用在哪 |
|------|------|--------|
| 群組內 | **6px** | chip 與 chip、標籤與它自己的控制項 |
| 群組間 | **24px** | 「製作職業」與「製作等級」之間。**要 4 倍差距才讀得出斷點**，12px 不夠 |
| 列與列 | **12px ＋ 一條 `border-top`** | 純靠間距在窄螢幕換行後就分不出來了 |

作法是包一層 `.jf-group`（內 6px），列本身 `gap: 8px 24px`（列間 8、群組間 24）。
靠右的群組用 `.jf-end { margin-left:auto }`，**但 640px 以下要取消**，否則會被擠出畫面。

順帶：多列篩選要包成一張卡（本站既有的 `.toolbar`／`.craft-tools` 就是這個樣式），
讓「這些是條件」與下方結果在視覺上分開；裸放在頁面上會跟結果糊成一片。

**另一條**：警示徽章在密集表格裡要 `white-space: nowrap`（避免一枚拆成兩行），
但在說明文字裡它是一整句話，nowrap 會在 320px 直接把版面撐破。
散文情境（`.note`／`.shop-hint`／`.pf-liq`…）要覆寫回 `normal`。

### 3.19 會反覆重繪的清單，排序鍵不可以是「會變的值」（2026-08-11，使用者指正）

`tools/market/` 的製作計畫原本每一層都依**金額由大到小**排。看起來很合理——
最花錢的先看到——但那份清單是**一邊操作一邊看**的：重新查價、改數量、
按一次「✓ 我已經有了」，成本就變，**整份清單當場重新洗牌**，剛剛在看的那一列
跑到別的地方去。愈常互動的清單，動態排序愈難用。

✅ **改成依物品 ID 遞增**。ID 不會變，順序因此永遠一樣；而且 FFXIV 的物品 ID
大致依資料片／等級遞增，同一階的材料本來就會排在一起，順帶有分組效果。

適用範圍＝站內所有材料列，一律吃同一支 `byItemId`：製作計畫的每一層、
三種攤平檢視（直接材料／全部素材／基礎素材／中間物）、簡易清單的原料 chip、
採買彙總、上下游配方。**一頁裡兩塊清單各排各的，對照著看會以為漏東西。**

**不要為此開排序選單**（使用者明確指定）。這裡沒有第二種排法值得使用者花心思挑，
多一個選單只是把決定丟回去。但**要讓人看得出「這是排過的」**——表頭給一句
`title="依遊戲內物品編號固定排序，不隨價格變動"`，否則會被當成隨機順序。
⚠ 不要為了「看起來像排序」而掛 `aria-sort`：那是可點排序表頭的語意，
欄位不可點卻宣告 `aria-sort`，對螢幕報讀器是假承諾。

> 反例對照：賺錢排行的表頭**是**可點排序的，那裡的 `aria-sort` 才成立。
> 「固定排序」與「使用者可排序」是兩種東西，別互相套用。

### 3.20 頁面 JS 長到一定程度就抽成同目錄的 `.js`（2026-08-11）

### 3.21 一列一筆的儲存清單，用折疊卡而不是三行文字（2026-08-11）

「我的清單」原本每份清單是一列 `.saved-row`：名稱、`4 項 · 更新於 …`、
再把內容截成 `A×1、B×1、C×1 …` 一行。**認不出是哪一份，也看不到完整品項。**

✅ 改成 `<details>` 折疊卡（外框沿用共用的 `.fold`，見 §3.18(d)）：

| 狀態 | 內容 |
|------|------|
| 收合 | 清單名 ＋ `N 項 · 共 M 件 · 更新於 …` ＋ **前 6 件的物品圖示**（`+N` 帶過其餘） |
| 展開 | 完整品項網格，每件可點 → 直接開該物品的市價視窗 |

三個要點：

- **「項」與「件」要一起給**：不同品項數與總數量常常差很多（4 項 120 件），
  只給其中一個會讓人誤判這份清單的規模。
- **圖示比截斷的文字好認**，而且不必展開就有辨識度——這才是「不單調」的解法，
  單純把內容藏進折疊只是把資訊搬走。圖示是輔助辨識，品名在展開後才是正式資訊，
  所以圖示列掛 `aria-hidden="true"`。
- **載入／改名／刪除留在 `<summary>` 裡**（最常用的是「載入」，不該逼人先展開），
  但**每顆鈕的 click 都要 `preventDefault()` ＋ `stopPropagation()`**——
  否則按「刪除」會順手把卡片展開。
- **展開狀態記在記憶體、不要進 localStorage**：改名／刪除會重繪整區，
  沒有記憶的話剛展開的卡會被收回去；但清單本身會增減，存進 localStorage
  只會留下一堆已刪清單的殘留鍵。

### 4.3c 社群來源要「對回遊戲資料」才算數（2026-07-24 定案）

鐵則是「台服官方優先、**社群繁中站次之**」——但「次之」不等於照抄。使用者給社群來源時（例：無人島動物來自
[steamxo](https://www.steamxo.com/2023/01/05/2700775)，附註「雖然是無官方確認，但資料應該是正確的」），
**先做結構性對位，別直接寫進資料檔**。無人島動物那次的三層驗證可以當範本：

1. **用來源沒給的欄位當對位鍵**。文章只有名稱／體型／時間／天氣／座標，沒有 row id。
   拿「體型＋稀有度＋兩項報酬素材的**先後順序**」對回 `MJIAnimals`，29 筆中 27 筆唯一命中。
   關鍵是**稀有度不是文章給的**，是從「常駐／與常駐同座標／座標獨占」推出來的 → 等於一條獨立約束。
   對位率高本身就是「這份資料是真的」的證據；對不上的那幾筆才是要查的。
2. **歧義用另一個維度解，不要猜**。奧猴／松鼠的報酬完全相同 → 抓 `Icon` 圖檔下來**看圖**判定
   （70123 靈長類大眼＝奧猴、70127 尖吻齧齒＝松鼠）。這比「哪個 sort 比較小」之類的推測可靠。
3. **名稱另找站內官方佐證**。29 個名稱的生物詞幹全部能在 `data/monsters.json`（`nameSource=tw-mobs`
   台服官方怪物名）找到同詞條 → 證明不是簡轉繁也不是臆測。

**外部來源會有錯，對位就是為了抓出來**：那篇有三處錯誤（時窗筆誤、兩欄對調、兩筆報酬與 datamine 不符）。
原則是**datamine 有的欄位一律以 datamine 為準**，外部來源只補 datamine 沒有的東西。
來源網址、等級（官方／社群）、驗證方法、已知錯誤全部寫進資料檔本身（見 `data/island-names-tw.json` 的
`_animalSource`），別只留在 commit message——換機之後只有 repo 內的東西跟得走。

**譯名 vs 數值要分開判斷**：動物「名稱」受譯名鐵則約束；但「出現時段／天氣／座標」是**語言中立的數值**，
任何可靠來源皆可，驗證方式是對回遊戲資料而非比對譯名。卡在譯名時先問一句「我缺的到底是名字還是數字」。

### 4.3d 例外：非物品的敘述字串可簡轉繁，但要標記且會出錯（2026-07-24）

使用者 2026-07-24 就無人島的**製作類型／建築／地區／分類**名指示「直接翻譯成繁體就好，大致上的文字應該是一樣的」。
這是使用者的決定，照做——但實作方式有講究：

- **只開給非物品字串**。凡是拿得到 `itemId` 的一律走 `items.json` 的台服官方名，**不因為這個口子開了就一起轉**。
- **轉出來的名字要標記來源**。`island-names-tw.json` 的 `_nameSourceBySection` 把各區塊標成
  `cn-hant`／`community-tc`／`tw-official`，`build-island.mjs` 寫成每筆的 `nameSource`，
  前端以虛線底線＋tooltip 標注「非台服官方譯名」。簡中原文保留在 `nameCn`，日後抄到實際用字可直接替換。
- **它確實會錯，而且錯得很像真的**。我逐字把 `开拓工房` 轉成「開拓工房」，但台服官方物品叫
  「**開拓工坊**酸泡菜／烤南瓜／水煮蛋」——是**工坊**。這是靠反查 `items.json` 才發現的。
  物品名的實例更多：`开拓用鹤嘴锄`→**開拓用十字鎬**、`高级捕兽用催眠球`→**高級捕獸用睡眠球**、
  `海岛红辣椒`→**海島紅彩椒**、`海岛西葫芦`→**海島櫛瓜**、`海岛西兰花`→**海島花椰菜**、
  `长臂虾`→**無人島長臂蝦**。全都不是換字能得到的。
- **能加護欄就加**。`build-island.mjs` 會檢查開拓等級解鎖敘述裡以「」括起來的詞是否為
  `items.json` 的台服官方物品名，不是且不在 `NON_ITEM_TERMS` 白名單就 **throw**——
  這擋的是「日後有人把簡中攻略整段貼進來」。已實測攔截。

**通用做法**：轉繁前先拿候選詞去 `items.json` 全文搜一遍，官方物品名裡出現過的用字就是官方用字。
這一招在本次抓到「工坊 vs 工房」，成本極低，值得每次都做。

### 4.4 天氣資料管線（重大 bug 教訓）
maps.json 的 `weatherRates` 由 `scripts/fix-mapkeys.mjs` 從 XIVAPI v2 回填。兩個關鍵事實（2026-07-02 修復）：
1. **XIVAPI v2 的 `WeatherRate.Rate[]` 已是「各段機率」**（加總=100），**不是**原始 sheet 的累進上界。當成累進相減會產生負值被丟棄，曾造成 66/67 張地圖天氣表殘缺（加總只有 30–45%）。
2. **天氣槽位順序不可合併同名天氣**——天氣種子演算法（`assets/js/eorzea-weather.js`）靠順序累加出 seed 區間，合併會位移邊界算出錯誤天氣。
- **天氣譯名唯一權威表**＝fix-mapkeys.mjs 的 `WEATHER_TC`（微風=Wind、強風=Gales、暴雨=Showers、雷雨=Thunderstorms、星磁暴=Astromagnetic Storms、月塵=Moon Dust）。`eorzea-weather.js` 的 `WEATHER_INFO` 名稱已對齊；**改任一邊必須同步另一邊**，否則 NAME_TO_KEY 反查斷裂、限天氣魚永遠比對不到。
- `fishes.json` 的 `weatherSet[].name` 是英文名，釣魚頁用 `EN_TO_KEY` 轉引擎 key 後比對。31 種魚 spotId=null 無法算天氣窗口。
- **`eorzea-weather.js` 的演算法已用獨立實作交叉驗證過（2026-07-24）**：與社群通用的 SaintCoinach／`WeatherFinder`
  版本比對 **22000 個天氣時段，seed 與天氣結果皆 0 筆不一致**，無名島（map 772）機率表也逐項吻合。
  **不必再懷疑這支的正確性**；天氣算錯時先查 `weatherRates` 資料與 mapId，不要重寫演算法。

### 4.5 資料信封與 patch 管線
（詳見 [DATA-SOURCES.md](DATA-SOURCES.md)、[../data/SCHEMA.md](../data/SCHEMA.md)。）
- 台服版本門檻＝`data/_meta.json` 的 `gamePatch`；前端 `assets/js/patch-gate.js`：`條目 patch > gamePatch → 隱藏`。
- 物品繁中名以 `tw-items.msgpack` 為準；對不到＝台服未開放 → 前端直接不顯示，**不可用 XIVAPI/簡中/英文補名**。
- patch 一律走 Teamcraft `patch-content`（XIVAPI row 不含 patch 欄）。
- **升版流程（2026-08-11 升 7.21 時實跑定案）**：
  1. `node scripts/build-tw-items-msgpack.mjs --apply` — 先刷新繁中名快照，**這步不做，後面全部白做**（見下一條）。
  2. `node scripts/build-items.mjs` — items.json 收下新物品（既有 patch 會被沿用，不會洗掉）。
  3. `patch-backfill.mjs`→`patch-backfill-all.mjs`→`patch-backfill-proxy.mjs`（dry-run 預設、`--apply` 寫入）→ `backfill-sources.mjs --apply`。
     gamePatch 由 `patch-backfill.mjs` 的 `TW_PATCH` 常數寫進 `_meta.json`，**改那個常數，不要只改 JSON**。
  4. `node scripts/patch-tw-names.mjs --apply` — 用 items.json 補新開放條目的繁中名（魚／園藝／鳥鞍／隨從）。
  5. 衍生檔：`build-items-lite`＋`build-items-market`＋`build-item-categories`＋`build-market-sources` → `minify-data --apply` → `sync-meta --apply`。
  6. `validate-data.mjs`（要 0 error）→ `validate-links.mjs` → `bump-sw-version.mjs`（動過 assets/）→ commit。
- **`gamePatch` 只有一個真實來源＝`data/_meta.json`（現為 7.21）**。文件若與它不一致，一律以 `_meta.json` 為準去改文件，**不要反過來為了對齊文件把 gamePatch 調上去**——那會讓台服尚未開放的條目被放行到前端。`patch-gate.js`（2 處）、`tools/market/market.js`、`scripts/validate-data.mjs`、`scripts/patch-backfill.mjs` 各有一份後備／門檻字串，升版時一併更新（`grep -rn "7\.21"` 可回查）。
- **台服到底在哪一版，用 Teamcraft 的台服語系檔反推，不要憑公告或印象**（2026-08-11 定案）。做法：拿 `tw/tw-items.json` 的 id 去對 `patch-content.json`→`patch-names.json`，看**最高的那個版本**。2026-08-11 實測：7.2 有 758 件、7.21 有 948 件、7.25 以上 0 件 → 台服當前＝**7.21**（台服把國際服 7.2＋7.21 併成一次更新）。只設 7.2 會把 520 筆 7.21 配方等內容繼續關在門外。
- **升版第一步是刷新 `out_data/tw-items.msgpack`，不是改版本號**（2026-08-11 教訓）。那份快照原本是「使用者提供、沒有腳本產它」的一次性檔，卡在 43,748 筆／7.15；閘門一開到 7.21，新開放的條目就地缺名：魚 8 筆 `name=null`（釣魚頁是 `f.name || f.nameEn` → 英文魚名見客）、園藝 2 筆顯示 `#47951`、隨從 4 筆與鳥鞍 1 筆整串英文。補法＝`build-tw-items-msgpack.mjs`（上游 45,548 筆，護欄：必須是既有快照的**超集**才寫入）。順帶修好 80 個舊譯名，其中多筆根本是簡中用語（馬蘇里拉乳酪→莫札瑞拉起司、面向收藏家的→給收藏家的、明日複明日→明日復明日）。
- **`build-minions.mjs` 的寵物道具篩選條件是 `category === "Minion"`，但 items.json 的分類早就是繁中「寵物」**——現在重跑它會 0 命中、全部退回英文名。要動 minions 前先確認這條。`patch-tw-names.mjs` 走的是同一套「companion 圖示編號 + 55000 ＝ 道具圖示編號」對法，可當參考。
- **不要為任何頁面關掉版本閘門**（2026-07-26 教訓）。釣魚頁曾把引擎的 `include` 覆寫成 `() => true`，理由寫「魚庫本身即台服可見範圍」——是錯的：`fishes.json` 有 35 筆 patch 7.2–7.5，`name` 全 null，而卡片是 `f.name || f.nameEn`，於是英文魚名直接露在頁面上。**`validate-links.mjs` 那行 `fishes.itemId → items 35/1449（台服未開放魚屬預期內）` 就是徵兆**——「資料層預期內」不等於「前端可以顯示」。看到某頁自訂 `include` 時，先確認它有沒有把 `PatchGate.released` 一起帶上。
- **「名稱有沒有中文字」不能當「台服有沒有開放」的判斷式**（2026-07-26 幻卡教訓）。幻卡頁的 `include` 原本寫 `/[一-鿿]/.test(c.name)`，結果把台服官方就用拉丁字母命名的 **11 張卡**（9S／2P／2B／N-7000／Ark Angel MR–EV／Prishe of the Distant Chains／Shadow Lord）判成未開放、整批消失。**正解是判斷「繁中名的來源有沒有給值」**：幻卡的 `name` 只來自台服 `items.json` 的卡片道具名，所以 `!!c.name` 就是「台服有這張」。同型的坑也修過樂譜頁（§4.9「顯示過濾放寬」，英文曲名）。引擎預設的 `e.name !== e.nameEn` 同樣會誤殺這種卡，**新頁面若資料源本身就是台服客戶端資料，請改成只判 `name` 有值**。
- **上游張數／筆數不要寫死在 build 腳本裡**（同一次教訓）。`build-triple-triad-all.mjs` 寫死 `TOTAL_CARDS = 425`，台服 7.1 開的 10 張新卡（編號 426–435）因此永遠抓不到，而且**不會報錯**。可回查的張數來源優先：幻卡＝`items.json` 裡 category「九宮幻卡」的道具數。補卡走增量腳本 `patch-triple-triad-new-cards.mjs`（dry-run 預設），不要為了 10 張重跑 60–90 分鐘的完整建置。
- **XIVAPI v1 已經停在舊版本**（2026-07-26 實測 `xivapi.com/TripleTriadCard/426` → 404）。**抓 7.1 以後的 sheet 一律走 v2**（`https://v2.xivapi.com/api/sheet/...`，且**必須指名 `fields=`**，不然 `fields` 回空物件）。v1 的 `GamePatch` 對新資料也不可信（幻卡有 11 張比實際偏早，例：黑貓標 6.5、道具是 7.01）——**patch 以台服道具的 patch 為準**。
- **粗略 `N.x` patch 是版本閘門的破口**：`patch-gate.js` 取主.次兩段做數值比較，`"4.x"` 解析不出次版號會被當成「未知 → 不隱藏」。`validate-data.mjs` 會 warn，看到就要修到 0。`orchestrion` 那 4 筆的修法（`fix-orchestrion-patch.mjs`）是**加後備來源**：ffxivcollect 對不到時退回 `items.json`（同一顆 itemId，tw-items 來源，精確到 x.y）。

### 4.6 大資料檔要為「實際用到的欄位」出精簡版（2026-07-23）
`data/items.json` 是 10MB／43748 筆 × 9 欄，但限時採集查詢與採集紀錄兩頁只用 `id→繁中名`，卻得整包載完才畫得出第一格。新增 `scripts/build-items-lite.mjs` 產 **`data/items-lite.json`（1.3MB，省 87%）**。
- 格式是 `data: [[id, name], …]` **配對陣列，不要用物件**：JSON 物件的 key 只能是字串，前端 `new Map(Object.entries(...))` 會把 id 變字串，害 `Map.get(數字 id)` 全部落空。
- **id 集合與 `items.json` 完全一致**，所以「查不到＝台服未開放 → 不顯示」這條規則在精簡版上等價；換檔前用兩頁的真實過濾邏輯比對過節點數與產物名輸出，完全相同。
- 需要 `marketable／ilvl／icon／category` 的頁面（市場查價）仍讀完整版。**重建 items.json 後記得一併重跑這支**。

### 4.6b 收藏品判定：只認 `IsCollectable`，不要看名字（2026-07-26 教訓）
**台服收藏品不一定叫「收藏用○○」。** 曾用這個前綴當分類器，結果把限時採集的收藏品節點 **76 個少算成 38 個**。
- 實查限時採集節點的 325 種產物：**48 種是收藏品卻沒有前綴**（火砂礫、雷砂礫、強火性岩、赤玉土、腐殖土、水薄荷、梅茵菲娜月桂、黑雷岩、陽風岩、金色樹枝、不定性結晶花…）；反向 0 種。**前綴是子集，只會漏不會誤判**——所以「用前綴抽樣看起來全中」不代表分類正確，一定要跟權威來源對數量。
- **本機沒有任何可用欄位**：`items.json` 的收藏品 `category` 一律「雜貨」、`rarity` 1、`marketable` false；`gathering.json` 也沒有。權威只有 **XIVAPI `Item.IsCollectable`**。
- ⚠️ **`AlwaysCollectable` 不是「專屬收藏品」**：64 個「收藏用○○」裡 48 個是 `false`。要判斷「能不能當收藏品採」只看 `IsCollectable`。
- **前端是靜態頁不能即時打 API**，所以旗標要烘成資料：`node scripts/build-collectable-items.mjs` → `data/collectable-items.json`（1023 筆、6.4KB，僅收 `items.json` 有的＝台服已開放者）。詳見 [SCHEMA §2.1b](../data/SCHEMA.md)。
- **節點層級的歸類**：一個採集點可能同時產收藏品與一般素材（實測 38 個這種混合節點），採「任一產物可當收藏品即算收藏品」，收藏品 76／素材 137 才會互補不重疊。

### 4.7 地圖底圖 key：`default/00` 是佔位圖，不是底圖（2026-07-26）
`maps.json` 的 `image.key` 來自 XIVAPI Map 列的 `Id` 欄（如 `a2fx/00`）。**若看到某張地圖的 key 是 `default/00`，那一定是錯的**——那是 XIVAPI 的空白羊皮紙佔位圖，畫出來是一張沒有地形的米色底圖，症狀看起來像「地圖不見了」（本機 `default_00.jpg` 根本不存在 → 404 → fallback 抓遠端才拿到那張空白圖）。
- **根因**：`scripts/fix-mapkeys.mjs` 以**英文地名**比對 Map 列、同名多列時取第一個。「The Diadem」「The Crown of the Immaculate」在遊戲裡都有多列 Map，其中一列的 `Id` 就是 `default/00`，剛好被抓走。已在該腳本加規則：**同名多列時佔位圖永遠讓位給有真實底圖的那列**。
- **既有資料修正**：`node scripts/patch-map-default-images.mjs`（dry-run 預設，`--apply` 寫入；會逐筆連 XIVAPI 查該列真實 `Id`，不憑印象填）。2026-07-26 修了 2 筆：584 雲冠群島 → `a2fx/00`、557 完璧王座 → `n4fb/00`。
- **改完記得確認底圖檔在不在**：`node scripts/download-maps.mjs --id <mapId>`。雲冠群島那張 `a2fx_00.jpg` 其實一直都在 `assets/maps/`，壞的只有 maps.json 指向。

### 4.8 魚王／魚皇：只有魚王有資料旗標，魚皇必須維護名單（2026-07-26）
FF14 的稀有魚分兩階，中文社群叫法與遊戲內名稱要分清楚：
- **魚王＝釣場之王**（日文ヌシ、英文 Big Fish）：綠色品質稀有魚。**有資料旗標**＝上游 fish-tracker 的 `bigFish`，已在 `fishes.json`，1414 種裡有 267 種（不含魚皇）。
- **魚皇＝釣場之皇**（日文オオヌシ、英文 Living Legend）：魚王中條件最嚴苛的一階，**每個資料片版本末期只追加 6 隻**（2.4／3.5／4.55／5.55／6.55），共 30 隻。7.x 的要等 7.55／7.56。

⚠️ **魚皇在遊戲資料與上游來源都沒有旗標，別想用欄位推**：
- XIVAPI `FishParameter` 的 `AchievementCredit`／`IsHidden`／`IsInLog` 在魚王與魚皇之間**完全相同**（海中老人 8753 與波太郎 8775 都是 `267 / true / true`）。上游 `data.js` 的 21 個欄位也只有 `bigFish`。
- **「需要魚識（`predators`，以小釣大）」不能拿來當判準**：只對重生之境與蒼穹之禁城成立，紅蓮／暗影的 6 隻裡各只有 3 隻需要魚識（紅龍就是不需要魚識的魚皇，卻是社群公認的「四大天王」之一）。
- 正解：名單寫死在 `scripts/patch-fish-legendary.mjs`（來源＝中文維基「釣場之皇」），標成 `fishes.json` 的 `legendary`。腳本內建健檢（id 要在、繁中名要對得上、且必須本來就是 `bigFish`），對不上就中止。
- **交叉驗證方式**（日後補 7.x 時可再用）：蒼穹／紅蓮／暗影／曉月的 6 隻，各是該資料片 itemId 最大的**連續 6 個**；重生之境是散落的例外。
- ⚠️ `build-fishing.mjs` 重建後 `legendary` 會整批歸零，**必須重跑 `patch-fish-legendary.mjs --apply`**，漏跑不會報錯、只會安靜地把 30 隻魚皇降級成魚王。

### 4.9 釣餌鏈的一段可能是「A 或 B 皆可」（2026-07-26 教訓）
上游 `bestCatchPath` 的每一段**不一定是數字**，也可能是 `[餌A, 餌B]`＝兩者皆可（82 條魚）。早期 `build-fishing.mjs` 直接 `.map(id => ({itemId: id, name: baitName(id)}))`，陣列那段就變成 `{itemId:[43849,43852], name:"43849,43852"}`——**itemId 型別錯掉、畫面直接印出 id 數字**，錯了不知多久沒人發現（星鯨的釣餌一直顯示「36597,36596」）。
- 現在的形狀：`{ itemId: 36597, name: "星塵／震撼板鉤", alts: [{itemId,name},…] }`。`itemId` 永遠是數字（第一個選項），多選項才有 `alts`。**任何用 itemId 比對釣餌的地方都要一併看 `alts`。**
- 既有資料用 `scripts/patch-fish-bait-alts.mjs` 就地修（壞掉的 itemId 陣列本身留著兩個 id，名稱回查 items.json，不必連外）。
- 同一個雷還留在 `predators[]`：它的 `itemId` 是 `[魚 itemId, 需要數量]`、`name` 是 `"8774,1"` 這種字串。**目前前端在顯示時自行拆解**（釣魚頁詳情彈窗），沒有壞掉的畫面，所以沒動它——但別直接信 `predators[].name`。

### 4.10 外部工具站的 id **不是**遊戲 id——一律用名稱比對（2026-07-28 教訓）

幻卡 `sources[].instanceId` 存的是 **Garland Tools 自家的 instance id**，不是 ContentFinderCondition id。
182 個裡有 64 個「剛好」也是 `dungeons.json` 的有效 key，**但其中 151 個對到的是錯的副本**：

| Garland id | Garland 是 | dungeons.json 同 id 是 |
|---|---|---|
| 96 | The Skydeep Cenote（神聖禁地深空天坑，7.0） | 巴哈姆特大迷宮 邂逅之章4 |

- **鐵則：跨來源接 id 前，先拿「名稱」對一次；對不上就別接。** 這是 PROGRESS §二之一「更危險的是對得到的」的第二次現身，第一次是 mapId 兩套 id 空間。
- 相對的，**這條也是最好的護欄**：`patch-dungeon-expansion.mjs` 用英文名對位 386/386 全對，才敢寫 `expansion`；`patch-collection-order.mjs` 同理（坐騎 362/362、寵物 581/581 英文名全對）。
- Garland instance id 分段：小 id＝Dungeons、**20xxx＝Trials（討伐戰）**、**30xxx＝Raids（大型任務）**、36xxx＝異聞迷宮。
- 同一支腳本還發現 **`treasureId` 其實是 `itemId`**，而且型別「藏寶圖」是上游標錯的（10 個裡 7 個是金碟幣卡包）。**欄位名不代表內容，看到可疑就拿值去查。**

### 4.17 三個「看起來像缺口、其實是已定案」的判斷（2026-07-29 定案）

每次稽核都會重新報這三項，先寫清楚結論，別再重查一次：

**(a) 一件裝備有多種取法，per-piece 只寫一個——這不是缺口。**
彈窗每件裝備下方那行是「一句話摘要」（人工整理的 `source`），
**完整清單另外走 `item_sources.js`**，呈現在彈窗底部的「📍取得方式總覽」，
篩選／搜尋也都吃那份（見 §4.x 的 build_item_sources 說明）。所以

### 4.19 資料檔裡有「沒有腳本會產生」的區塊＝重跑腳本就會洗掉（2026-07-29，小隊頁的教訓）

`data/squadron.json` 有 60 筆 `kind:"recruit"`（可徵募的 NPC 隊員），但 `scripts/build-squadron.mjs`
只產 mission/training/chemistry/chemistryCondition/tactic/memberGrowth 六類。
**跑一次 build 就會把 60 筆隊員整組洗掉**，前端 NPC 選單直接空掉，而且不會有任何錯誤訊息。

- 已把 60 筆內嵌回腳本並加驗證（職業／種族／id 重複），改完用 round-trip 比對確認一字不差。
- **通則**：`data/*.json` 的每個 `kind`／區塊都該有腳本負責產生。改資料前先問
  「這份檔案重跑 build 會不會少東西」——`node scripts/build-<x>.mjs` 後跟舊檔 diff 一次最快。
- 同類風險：任何「手工補進 JSON、沒回寫腳本」的欄位都一樣。要補就補進腳本，別只改 JSON。

**順帶三條小隊頁專屬的坑**（都是 07-29 實測抓到的）：

1. **面板數字與計算用的不是同一組人**：總值面板算全名冊、任務列表寫死 `roster.slice(0,4)`。
   凡是「有名冊、但只有部分成員參與計算」的頁面，**參與組不能靠陣列順序隱含**。
   最後的解法不是加勾選，而是**每個任務各自從名冊算出最佳 4 人**（C(8,4)=70 組全掃，
   排序依「等級接得了 > 成功率 > 屬性餘裕」）——計算機本來就該自己算，手動勾還會漏掉更好的組合。
   面板改成「名冊能力上限」：三項各自取最好的 4 人，並標明三項通常不是同一組人。
2. **選單接上了 state，卻沒接上計算**：吉兆「條件」存進了 roster，但 `getActiveMembers()`
   組物件時漏帶 `chemCondId`，計算端讀到 `undefined` → 一律當成立。
   UI 上還有個「觸發」badge 走另一條路徑，看起來像有在動，其實跟數字無關。
   **驗這種東西要比對「換設定前後的計算結果」，不能只看畫面有沒有變。**
3. **上限攔截被 `Math.max(0,…)` 吃掉**：訓練池超上限時要從其他屬性扣，但其他屬性歸零後
   `Math.max(0, 0-20)` = 0，總和就攔不住了，連點會一路衝到 480/400。
   夾上限要算「最後的總和」，不要只對單一項目做非負保護。
   另外**屬性之間的轉換是以 20 為一個單位，扣的對象是「這次沒被訓練到」的屬性、且各項平均分攤**
   （使用者指定的原則）：基礎訓練在上限時成為 +40/−20/−20、組合訓練成為 +20/+20/−40，
   與 `squadron.json` 的 `deltaAtCap` 一致。
   這條規則錯過兩次：先寫「按現值比例扣」（生出 233 這種非 20 倍數的值），
   再寫「每次從數值最多的那項扣 20」——後者在兩個未訓練屬性數值差很多時會把 40 全扣在同一項
   （心智 260／戰術 20 → 心智 −40、戰術不動），正解是各扣 20。
   **教訓**：「以 N 為單位」和「從誰身上扣」是兩條獨立的規則，滿足前者不代表後者也對；
   驗收案例要刻意把兩個來源的數值拉開，才分辨得出實作走的是哪一種。
4. **同一件事要更新三個面板 → 遲早漏一個**：訓練池一動要更新池子本身、能力上限、任務成功率。
   分成三支各自呼叫時，驗收腳本就漏掉其中一支，畫面出現「面板說 0、成功率還照舊」的矛盾，
   一度被誤判成計算 bug。**收斂成一支 `refreshAfterPoolChange()`**，呼叫端不必記得有幾塊要更新。
5. **只顯示「門檻」不顯示「我有多少」**：任務列表原本只給門檻與「差 N」，使用者要心算才知道現況。
   凡是「達標與否」的呈現，**兩個數字都要出現**（`實際 / 門檻`），顏色只是輔助。

**表格版型的坑（2026-07-29 補）**：`<table>` 預設 shrink-to-fit，窄螢幕下**不會**觸發外層的
`overflow-x:auto`，而是壓縮欄寬把中文欄位擠成一行一個字（手機頁高一度從 5405 暴增到 8096px）。
**表格一定要給 `min-width`**，它才會改成在容器內橫向捲動。`position:sticky` 的表頭在這種
「外層 overflow-x:auto」的結構下也不會生效——那個容器本身不垂直捲動，設了是死碼。

**遊戲規則本身的兩個註記**（查證後才寫，別再憑印象）：

- **隊員可以轉職**：〈戰鬥技巧教材〉守勢→劍術師/斧術師、攻勢→格鬥家/槍術師/弓箭手/雙劍師、
  魔法→幻術師/咒術師/秘術師，各 3000 軍票、需一等軍銜。轉職保留吉兆效果與等階，但會掉經驗值。
  → 隊員屬性要吃「當前職業」，不是 recruit 的初始職業。
- **任務等級門檻查不到可靠說法**：wiki 沒寫，社群一說「至少一人達標」一說「全員」。
  所以做成**警示不歸零**（顯示「⚠ 隊員等級不足」但仍照屬性算成功率）。
  **沒把握的規則就別硬編進計算**，寧可標出來讓使用者自己判斷。

### 4.15 binary 檔要在 `.gitattributes` 標 binary，否則 autocrlf 會安靜弄壞它（2026-07-28）

repo 一直沒有 `.gitattributes`，而本機 `core.autocrlf=true`。git 靠「前 8000 bytes 有沒有 NUL」
猜檔案是不是文字，**msgpack 開頭若剛好沒有 NUL（純中文字串表就會這樣）就被當成文字**，
checkout 時把落單的 LF 換成 CRLF：

| 檔案 | blob | 工作區 |
|---|---|---|
| `out_data/tw-items.msgpack` | 1,353,731 | 1,353,732（+1，Python/Node 都解不開） |
| `out_data/places.msgpack` | 596,170 | 596,203（+33） |

**最陰險的是 `git status` 一直顯示 clean**（回寫時又轉回去了），所以看不出來；
症狀是 `node scripts/build-items.mjs` 之類的腳本突然 `UnicodeDecodeError`。

- 已加 repo 根的 `.gitattributes`，把 `*.msgpack` 與各種圖片／字型／壓縮檔標成 `binary`。
- **檢測方法**：比對「工作區檔案大小 vs blob 大小」，binary 檔不該有差。
  （全 repo 掃過一次，只有這 2 個檔中招；PNG/JPG 因為開頭就有 NUL 而倖免。）
- **修復方法**：`git cat-file blob <sha> > 檔案` 直接寫回，不要靠 `git checkout`（stat 快取會擋）。

#### 4.15b 同一個 autocrlf 也弄壞了 SW 的 CACHE_VERSION（2026-07-29）

`.gitattributes` 只解決了二進位檔，**文字檔仍然沒有 `text=auto`**，而 `core.autocrlf=true`。
所以工作區的 css/js 是 CRLF 還是 LF，取決於它上次是被 git checkout 出來、還是被工具重寫過
——實測那 15 個檔案是**混的**（6 個 CRLF、9 個 LF）。

`scripts/bump-sw-version.mjs` 原本直接雜湊 `readFileSync()` 的**原始 bytes**，於是：

| 同一份內容 | 算出來 |
|---|---|
| 照工作區現況（混合換行） | `sgt-d99ca5124e` |
| 全部正規化成 LF | `sgt-e7de43a2f6` |

→ 換台電腦或重新 clone 就誤報「版本過期」，bump 完換回原本那台又報一次，
**CACHE_VERSION 在兩個值之間無限來回，而每次來回都會清掉使用者的全站快取**。
2026-07-23～07-29 就是這樣漂的（07-29 那次「順手補上」其實補錯了方向，值對不上任何一邊）。

- **已修**：`bump-sw-version.mjs` 改成先 `.replace(/\r\n/g,"\n")` 再雜湊，只認邏輯內容。
- **驗證方法**：故意把幾個檔案的換行翻面（CRLF↔LF），`--check` 應該仍然說「已是最新」。
- **通則**：**任何拿檔案內容算雜湊／比對的腳本，都要先正規化換行**，否則在這個 repo 一定跨機漂移。
- 還沒做：`.gitattributes` 加 `* text=auto eol=lf` 並全庫 renormalize。那會產生一次巨大的
  換行 diff，且要小心別波及已標 binary 的檔，暫緩；上面的正規化已讓症狀消失。

（進 `tools/glamour/data/OCR無解清單.md` 而非靜默消失），要補得等上游收錄。
**看到這類「查無此道具」先確認是不是這一類，不要當成判讀錯誤去改名。**

### 4.24 模糊比對「找不到」時退回最像的一個＝靜默給錯答案（2026-08-12，染色表的教訓）

染色白名單 `dye_names_ja.json` 與日→繁對照 `dye_ja_to_zh.json` **全庫只有讀取者、
沒有任何寫入者**，所以台服每次加新色它們都不會長，一路凍在 146 色。真正的傷害不是
「新色顯示不出來」，而是 `ocr_check.snap_dye()` 是模糊比對——**對不到不會留白，
會退回最像的舊色**：

| 圖上實際 | 前端顯示 | 件數 |
|---|---|---|
| メタリックルビーレッド | 寶石紅（ルビーレッド） | 58 |
| メタリックダークブルー | 黑暗藍 | 45 |
| メタリックコバルトグリーン | 金屬綠 | 43 |

同一個機制還讓**純色系殘字**被硬指派：`similar()` 對「一方是另一方的子字串」一律回
0.95，所以「グリーン」→アダマンタスグリーン（36 次）、「レッド」→ダラガブレッド（37 次）
——綠色染劑有十幾種，挑到哪個純屬偶然。

**三個通則**：

1. **模糊比對表要有產生腳本，並列進換版流程**。手工維護的對照表不會有人記得更新，
   而它壞掉時**不會報錯**。本次補了 `tools/glamour/scripts/build_dye_names.py`
   （主庫 → 白名單＋日繁對照＋英文別名），改版後必跑。
2. **「找不到」的正解是回 `None`，不是回最像的**。要退回最像的，就得同時檢查
   「像得夠不夠有意義」——本次加了 `FRAGMENT_RATIO=0.6`：子字串命中時 token 至少要有
   候選名的六成長，否則判定不可信。完整色名不受影響（它在白名單裡有精確命中）。
3. **別為了多救幾筆而放寬模糊比對**。實測「對英文別名也做模糊比對」能多救 42 個，
   但其中 15 個是誤配（`RE`→アダマンタスグリーン、`RB`→モルボルグリーン、
   `Purple`→カラントパープル）。改用兩條窄規則（精確查表 ＋ 長度 ≥4 的唯一整詞前綴）
   只救 27 個但零誤配——**寧可少救，不要製造錯答案**。

**染色分類裡不是每筆都是顏色**：`categoryId 55（染料）` 底下同時裝著色素（ピグメント）、
生漆／黒漆、伊修加德重建用的上級色素。判定可染顏色要**同時要求日文名以 `カララント:` 開頭**，
否則那 12 筆會進白名單並把殘字吸走（「イエロー」→イエローピグメント）。

**繁中色名要去掉「染劑」字尾與「EX」前綴**：道具名是「EX無瑕白染劑」，但彈窗顯示的是
顏色本身「無瑕白」；EX 版與一般版是同一個顏色、只是道具不同（ピュアホワイト 與
ピュアホワイトEX 都顯示無瑕白）。另注意日英命名是錯開的——**日文的 `〜EX` 對應英文的原名，
日文無後綴的才對應英文 `General-purpose 〜`**。

### 4.23 查日文道具名要同時搜「本地 msgpack ＋ 備選庫」（2026-08-09 踩過）

`out_data/ja-items.msgpack` 沒有 7.x 新裝備；那些只存在於

### 4.24 「幾步才做得到」的東西要解最短路徑，不要列配方（2026-08-12，園藝頁的教訓）

舊的園藝頁對「薩維奈圓蔥」只印 `240h`，而實際是 **480h**。錯在三個地方，每一個都不是版面問題：

1. **配種收到的是種子不是作物**——本株那格仍然長本株自己的作物，只是收成時額外掉出目標種子，
   **還要再種一輪**才有目標作物。任何「查表印一個時數」的做法都會少一半。
2. **父本自己往往也是配種產物**，只列一層等於把問題丟回給使用者。
3. **同一個目標有多組配方、成本差很多**（薩維奈圓蔥是 264／264／240 小時），列出來不挑等於沒幫上忙。

**How to apply**（同樣適用於任何長鏈製作／兌換）：

- 成本模型：`cost(種子) = 0 若可直接買／採；否則 min over 配方 of max(cost(本), cost(鄰)) + 本株作物時數`。
- **用定點迭代求解，不要用遞迴 memo。** 配種關係有環（血椒 ↔ 魔蕨菜那一區），
  遞迴會把環上算出的 `Infinity` 記進 memo，害整條鏈都變成「無解」——第一版就是這樣，
  血椒與魔蕨菜兩筆直接顯示 `Infinity`。改成迭代到不動點後兩筆各是 23 天、28 天。
- **「可直接取得」不能認市場板。** 市場板對每個種子都成立，認了它整棵樹會縮成一層，等於沒算。
  只認 NPC 商店／採集／任務，市場板另外標成捷徑提示（107 個種子裡 30 個是真的只能配）。
- 輸出要**階段化**（同階段可並行、時間不疊加）並算**尖峰佔用格數**（區間掃描），
  否則使用者不知道要準備幾格園圃。

### 4.25 量對比要保留 alpha 逐層合成，否則會報一整頁假失敗（2026-08-12）

本站大量用半透明底（`--raise` 0.045~0.05、`--*-dim` 0.10~0.16）。量測腳本若把
`rgba(255,255,255,0.05)` 當成不透明色，量到的背景就是**純白**；`.chip.ok` 的
`rgba(74,222,128,0.12)` 會變成**純綠**、和文字色一模一樣 → 報 `1.00:1`。
第一版量測就這樣一次噴出 **108 類**未達標，全是假的。

**How to apply**：
- `parse()` 要保留 alpha，往上收集各層背景後**從最底層往上合成**（`fg*a + bg*(1-a)`）。
- **跳過 0×0 的元素**。收合的 `<details>` 內部元素 `getComputedStyle` 仍回報可見，
  但沒有版面；不跳過就會拿到一組沒有意義的背景。要驗它們就先
  `document.querySelectorAll('details').forEach(d=>d.open=true)` 再量。
- 驗收前後都要跑同一支腳本比對數字，別只看「有沒有紅字」。

### 4.26 headless Edge 量不到的兩件事（2026-08-12，差點寫出假報告）

**① 模擬不了 `pointer: coarse`。** `Emulation.setEmulatedMedia({features:[{name:'pointer',value:'coarse'}]})`
會被收下（回 `{}`、不報錯），但 `matchMedia('(pointer: coarse)').matches` 仍是 `false`——
**放在 `Page.navigate` 之後也一樣**。於是 tokens.css 的 `@media (pointer: coarse){ min-height:44px }`
根本沒套用，量到的全是桌機尺寸（第一次量到「`.quick-btn` 33px、`summary` 19px」就是這樣來的，
差點當成 bug 去修一個本來就沒問題的東西）。
**可行做法**：讓靜態伺服器把 **CSS 與 HTML**（頁面自己的 `<style>` 也有這個媒體查詢，只換 `.css` 會漏）
裡的 `(pointer: coarse)` 字串換成 `all` 再送出，量到的就是觸控裝置實際會看到的版面。
切換這個開關要**在啟動時就決定**（跑到一半才改，瀏覽器已經拿過那份 CSS 了，
即使 `Network.setCacheDisabled` 也救不回來——直接開兩個 process 跑兩趟最省事）。

**② `:focus-visible` 不吃程式呼叫的 `el.focus()`。** 用迴圈 `el.focus()` 檢查焦點環會得到
「整排 `outline-style: none`」的假結果。要用 `Input.dispatchKeyEvent` 送真的 Tab
（`rawKeyDown` + `keyUp`，`windowsVirtualKeyCode: 9`）再讀 `document.activeElement` 的 computed style。

**通則**：量測腳本報出「一大片同類型元素全部不合格」時，先懷疑探針，不要先改頁面。

### 4.26b 攻略站的資訊在圖片裡時：下載回來自己看（2026-08-12）

查園圃格位排列時，`WebFetch` 三個來源都回「沒有這個資訊」——wiki 只寫格數，
ffxivgardening 的格位圖是 **PNG**，WebFetch 轉 markdown 只留下檔名。差點下結論「查不到」。

**解法**：叫 WebFetch **列出頁面上所有圖片 URL**（不要它摘要），用 node `fetch` 把圖抓下來存檔，
再用 **Read 工具看圖**。`5x3-poor-man.png` 一打開就看到「Empty Deluxe Garden Patch (8 bed patch)」
配 3×3 的格線、中央放 STEP 標籤 ⇒ **高級園圃＝3×3 的外圈，中央不是田**。
編號再從另一張圖的步驟文字反推（「1 號格相鄰的是 2 號與 8 號」等三處互相吻合）⇒ 順時針。

**How to apply**：攻略站、wiki、論壇的關鍵資訊很常在圖裡（配置圖、流程圖、對照表截圖）。
「WebFetch 說沒有」只代表**文字**裡沒有。抓圖 → Read，是常規手段，不是最後手段。

### 4.27 「可以直接買到」不能把一次性來源算進去（2026-08-12）

園藝頁想給「這個不必種，直接買就有」的省時提示，第一版直接拿 `resolveSources()` 的非市場板結果，
於是**薩維奈圓蔥被標成「本身就能直接取得」**——那筆來源是 `quest`（任務獎勵），一次性的，
這輩子只拿得到一次。寫上去等於騙人。

**How to apply**：凡是「這東西容易拿」「不必自己做」這類**建議性**結論，來源要先濾掉
`gate.kind === 'once'`（任務一次性）與 `'rng'`（副本掉落／寶箱）。`accessOf()` 已經有這個分類，
用它就好。加上過濾後「產物可直接取得」由 64 種降為 51 種。
反過來說，**成本／難度**的計算則不能只看有沒有門檻，那是另一回事（見 §4.24 的葉節點判準）。

### 4.28 「去重」要看那份清單代表什麼——逐件染色去重＝把資料刪掉（2026-08-23）

幻化配裝的染色有**兩份形狀不同的清單**，先前用同一套去重邏輯處理，結果錯了一份：

| 清單 | 語意 | 去重對不對 |
|---|---|---|
| `mirapri_dyes.json`（整套 fallback） | 「這套用到哪些顏色」的**色票清單** | ✅ 對，重複沒有意義 |
| `mirapri_piece_dyes.json`（逐件 dye1/dye2） | 這一件的**兩個染色槽**，有順序 | ❌ 錯，兩槽同色是有效資料 |

FFXIV 的可染裝備有兩個獨立染色槽。兩槽都染同一色時，去重會讓第二槽變成 `—`，
前端只顯示一個顏色——**顏色本身是對的，但照著配的人不會知道第二槽也要染**，
留白預設色穿出來就不一樣。全庫 250 件受害，佔 Claude 親讀雙槽件的 16%。

同一個 bug 抄在四個地方（`ocr_check.clean_pieces`、`apply_dyes._zh`、
`reconstruct_empty` 三處 inline），已收斂成 `ocr_check.dyes_to_zh()` 一支。

**改的時候有兩個坑，直接拿掉去重會壞事**：

1. **黏在裝備名後面抽出來的染色仍要去重**。`_split_item_dye()` 會把混進裝備名的
   色名切出來，它常常與 `dyes` 清單裡的同一色重覆（全庫 **655 處**）。無條件保留重複
   ＝憑空造出 655 件假的雙槽。正解是「`dyes` 清單內不去重，`extracted` 併入時才去重」。
2. **同一件裝備被兩個 OCR 條目對到時要「先到先贏」，不要合併**（全庫 13 次）。
   多半是面板重覆列同一件，也有 `best_match` 錯配（`ヨルハ五三式軍装:医` 貼到 `軍帽:医`）——
   合併會把別件的顏色混進來。

**How to apply**：動任何 `dict.fromkeys(...)` 之前先問「這份清單的重複代表什麼」。
是集合（有哪些顏色／有哪些來源）就去重；是**有序的槽位**（第一槽/第二槽、主手/副手）
就不能去重。驗收方式是**改前改後逐件 diff**，並把「非預期的變化」分類計數——
本次 35,209 件裡只有「補上第二槽（與第一槽同色）250 件」，其餘四類非預期變化全部 0。

### 4.29 移植別人的規則引擎，要**連他的測試一起搬**（2026-08-25，製作模擬器）

**Why**：製作公式的取整點極多（基礎值 `floor`、效率 `fround`、增益相乘後再 `floor`），
差一個 `Math.floor` 在高階配方上差幾百品質，而且**畫面上完全正常**——沒有任何症狀會告訴你算錯了。
自己隨手排兩套循環比對「看起來合理」根本驗不出來。

**How to apply**：

1. **把來源專案的測試檔一起抓下來，把期望值改寫成本站的驗證腳本**。
   `scripts/validate-craft-sim.mjs` 就是照 Teamcraft `test/simulation.spec.ts` 改的。
   首跑 67/68，唯一不符的那項正好是**移植時最容易漏的一條**——專心致志在非高品質狀態下
   被集中加工／集中製作／秘訣用掉時要消失，因為原作把它寫在 buff 的 tick callback 裡，
   照著類別逐個搬會漏掉。**沒有那個測試就不會發現。**
2. **能對到官方資料的欄位要另外對一次**。技能的 CP 與解鎖等級在 XIVAPI 的 `CraftAction`／
   `Action` sheet 查得到，建置時逐項比對（目前 36/36 相符）；效率查不到，只能信社群常數——
   **哪些有官方背書、哪些沒有，要在資料檔的 `source` 與文件裡寫清楚。**
3. **刻意的偏離要寫在程式碼檔頭＋文件兩邊**，否則下一輪維護會被當成 bug「修」回去。
   本站有兩處：隨機模式真的擲作業狀態（原作每步重設成「一般」，那是重播用的）、
   官方說明寫「不消耗一次作業時間」的技能不推進作業狀態。
4. **自己宣稱可行的東西（範本、預設值）也要進回歸**。頁面內建的四套循環全部在
   「宣稱的驗證條件」下實跑，必須完成且沒有任何一步被跳過。

順帶一條：**憑印象排的巨集不要當範本**。這次憑印象寫的四套在引擎裡實測全都做不完
（進度差 1500 以上），最後是用離線兩階段 beam search 解出來的——
先作業後品質**必須分兩階段**（單純 beam 會被進度帶走，品質技能的報酬要先疊內靜才兌現），
評分**必須把增益的剩餘步數算進去**（否則永遠不會去點改革：花 18 CP、當下品質零成長）。
細節見 [docs/crafting-sim.md](crafting-sim.md)。

### 4.30 `<span>` 當進度條會畫成寬 0——版面一定要量，不能只看截圖（2026-08-25）

**Why**：製作模擬器的四條進度條，`.bar-track` 與 `.bar-fill` 原本都是 `<span>`。
非替換型 inline 元素**不吃 `width`／`height`**，所以填色寬度是 0。
畫面上看起來就是「一條空的進度條」——很像「數值真的是 0」，截圖掃過去不會起疑。

**How to apply**：新做的任何「用寬度表達數值」的東西（進度條、比例尺、甘特條），
驗收時**量 `getBoundingClientRect().width` 與 `backgroundColor`**，不要只看截圖。
包在 flex／grid 裡的子元素會被 blockify，但**再往內一層就不會**——這次 `.bar-track`
是 grid item（自動 blockify、看起來正常），`.bar-fill` 在它裡面就中招了。

### 4.31 自動求解要**自己擋掉靠運氣的技能**——引擎不會幫你擋（2026-08-26，製作模擬器）

**Why**：引擎在理想模式（`linear: true`）下**不檢查 `requiresGood`**（跟 Teamcraft 一樣，
那是給人工排循環用的）。第一版求解器直接照引擎的結果搜，解出來滿滿都是集中加工／集中製作
——那些技能只有在高品質球色時能按，實際貼進遊戲整段用不出來。同理成功率 <100% 的
高速製作／倉促／冒進在理想模式下必成功，排進去會解出「看起來漂亮、實際常炸」的循環。

**How to apply**：**求解類功能的產物是「照著跑就成立」的東西，就要自己定義可用技能集合**，
不能沿用「模擬器允許什麼」。本站的規則是：成功率 <100%、吃球色的、以及只為了假造球色而
存在的技能（專心致志）一律不排；並在回歸驗證裡逐項檢查產出的循環沒有這些技能。
另外**評分要先把超過上限的部分砍掉**（`min(quality, recipe.quality)`）——不砍的話
低階配方會解出「品質 21300／目標 3360」的 17 步循環，多出來的九步毫無作用。
見 [crafting-sim.md §5b](crafting-sim.md)。相關：[[port-engine-with-its-tests]]。

### 4.32 同特異度時後面的規則勝——分寬度的覆寫要寫在本體那一段（2026-08-26）

**Why**：製作模擬器把結果條從「固定浮在畫面下緣」改成「寬螢幕收進卡片底部」時，
`position: static` 的覆寫寫在檔案前段的媒體查詢裡，而 `.result-bar { position: fixed }`
本體在後面——同特異度、後者勝，整條覆寫被吃掉。畫面上的症狀是「明明寫了 static 卻還在浮」，
看 CSS 不會發現，要開 DevTools 看計算後的值才知道。`body.has-result-bar` 的
`padding-bottom` 也同一個坑，害整頁多出 149px 的空白。

**How to apply**：要依寬度分兩種行為時，**把兩個分支都寫在該規則的本體那一段**
（`@media (max-width: …)` 與 `@media (min-width: …)` 相鄰），不要散在檔案兩端。
驗收方式是**量**：`document.documentElement.scrollHeight - clientHeight` 應為 0、
元素的 `getBoundingClientRect()` 要落在容器內。

### 4.33 關著的 `<details>` 內容仍有版面盒，但樣式不重算——量到整片假失敗（2026-08-26）

**Why**：製作模擬器的對比探針突然在亮色主題報 5 個未達 AA，其中「巨集」這個 h3 只有 **1.20:1**。
實際打開頁面完全正常。追下去發現那些元素都在**關著的 `<details>`** 裡：
現行 Chrome 不再用 `display:none` 藏 details 內容，元素**還有版面盒**（`getBoundingClientRect()`
回非 0），但主題切換後**不會重算樣式**——`getComputedStyle` 讀到的是上一個主題的顏色
（實測 `color` 還是暗色主題的 `rgb(232,234,240)`）。

**How to apply**：量對比／版面前，**要嘛把 `<details>` 展開再量，要嘛跳過 `el.closest('details:not([open])')`**。
更通則的版本已經記在 [[headless-edge-measure-limits]]：**整排或整片失敗時先懷疑探針**，
尤其是「畫面看起來正常但探針說爛掉」的時候。同一類的還有半透明底沒合成（見 §4.30 一帶）。

### 4.34 日文標籤糊到讀不出來時，先找同投稿者的**英文版截圖**（2026-08-27）

**What**：Mirapri 判讀遇到低解析度圖時，在放棄之前先查同一投稿者有沒有貼「English version」
的同一套截圖；有的話改讀英文名，再用 `scratchpad/en_to_ja.py`（`en-items.msgpack` ＋
`item_fallback_multilang.json`）轉回日文正名。

**Why**：日文標籤是漢字＋片假名，字符筆畫密；同樣被壓到 7px 的高度，拉丁字母還讀得出來，
日文已經糊成一團。實例：#026／#027 是 800×565 的三視圖合成、API 空殼套（清單也救不了），
日文版只認得出前兩件；同投稿者的 #028／#029 是同兩套的英文版，**12 件全部讀出來**，
回查道具庫 12/12 命中。而且順便修正了兩處我在日文版上的字形誤判——
`コンヴォーカー…` 其實是 `コンヴォカーサイブーツ`（id 33986）、
`彼岸紫岸` 其實是 `彼岸此岸【妖】`（id 40103）。**猜對的機率遠低於查對的機率。**

**How to apply**：
1. 圖糊 → 先看 `ocr_todo_new.json` 附近幾筆的 `title` 有沒有 `English version` 之類的字樣
   （這類投稿者通常會日英各投一次，時間戳相鄰）。
2. 讀英文名 → `py en_to_ja.py "Convoker's Thighboots" ...`，只採**完全命中**的。
3. 兩張圖都寫進快取（它們是兩筆獨立投稿，各自都要有自己的判讀）。
4. 英文版沒有、又真的讀不出來的 → 照舊留白並記進 `OCR無解清單.md`，**不要猜**（§4.20b）。

同一個道理反過來也成立：英文名回查是**精確查表**，不是模糊比對——查不到就是查不到，
不要退而求其次挑「最像的」，那正是 §4.24 那條的病。

### 4.35 前端大資料檔：屬於「道具」的欄位不要每件抄一份（2026-08-28，幻化配裝圖鑑）

`mirapri_outfits.js` 曾經 11.9MB（gzip 1.95MB）、瀏覽器光把它當 JS 原始碼編譯就要
**235ms**（中階手機 3–5 倍）。原因不是套數多，是**每件裝備都把道具本身的屬性再抄一次**：
6,860 套／35,249 件，但只用到 **6,347 個不重複道具**，而 `zh`／日文名／部位／版本／等級／
職業／取得方式／可染／可交易全都是道具的屬性，不是「這一套」的屬性。真正屬於這一套的
只有「哪件道具」＋「染了什麼色」。

**判準**：一個欄位如果由 `iid` 就能決定，它就該進共用字典、不該逐件複製。
（`item_sources.js` 早在 2026-07-19 就用對了這招——以裝備 ID 外連取得方式；
只是當時沒有把同一個道理套到其他欄位。）

抽成 `item_db.js`（每個 iid 一列）＋ 每件只留 `[iid, 染色1, 染色2, 旗標, 例外]` 之後：

| | 前 | 後 |
|---|---|---|
| raw | 11.9MB | 2.2MB ＋ 字典 0.7MB |
| gzip | 1,948KB | 660KB ＋ 字典 179KB |
| 解析 | 235ms | 17ms |

**三條做法上的鐵則**：

1. **編碼必須無損，而且要程式自己驗**。資料裡確實有同一個 iid 在不同套帶不同值的情況
   （多半是空殼重建的套缺欄位），所以字典存**眾數**、不同的那件逐欄記進 `ovr`
   （`null` ＝「這件沒有這個欄位」）。`build_site.py` 每次建置都把編碼結果解回來跟原始結構
   完整比對，對不上就 `SystemExit` 中止。**沒有這個閘門不要做這種轉換**——少一個欄位
   在畫面上完全看不出來，只會變成某一欄空白，然後一路傳到線上。
2. **解回來的形狀要跟以前一模一樣**。前端 `rehydrateMirapri()` 還原成原本每件一個完整
   物件，於是渲染／篩選／搜尋那 1,400 行**一行都不用改**。要動的只有載入那一段。
3. **格式定義只能有一份**。編解碼放 `tools/glamour/scripts/mira_codec.py`，
   `build_site.py` 寫、`build_review.py` 與 `check_duplicates.py` 讀都經過它；
   前端解碼在 `index.html` 的 `rehydrateMirapri()`，欄位順序必須與 `ITEM_DB_FIELDS` 一致。
   另外 `build_item_sources.py` 原本是**自己 parse 那三份 js** 抓裝備 ID 的——格式一變它會
   安靜地抓到 0 件、讓所有裝備退回單一取得方式，所以順手改成「讀 `item_db.js` 的 key」
   並在抓不到時直接 `SystemExit`。**會被別的腳本 parse 的產出檔，改格式時要一起盤點。**

### 4.36 圖片要分「卡片層」與「彈窗層」，一份圖餵兩個用途一定有一邊是浪費的（2026-08-28）

幻化配裝圖鑑的 `配裝圖片/縮圖/` 一份 619×1100／平均 90.6KB 的 JPEG 同時餵卡片格子與彈窗
大圖。彈窗需要這個尺寸，但卡片在桌機 6 欄時只有約 230 CSS px 寬——**一頁 60 張卡要載
5.3MB 圖片**，比整份社群資料（gzip 1.9MB）還重，而且這件事在任何 JS profiling 都看不到。

分兩層（`tools/glamour/scripts/build_image_tiers.py`）：

| 用途 | 目錄 | 規格 | 一張 | 6,963 張 |
|------|------|------|------|---------|
| 卡片 | `配裝圖片/卡片/` | 寬 320px **WebP** q74 | ~23KB | 170MB |
| 彈窗 | `配裝圖片/縮圖/` | 原尺寸 **AVIF** q50 | ~40KB | 280MB |

原本 616MB 的 JPEG 換掉之後**淨少 177MB**，一頁圖片流量 5.3MB → 1.4MB。

- **格式分開挑**：卡片層是 99% 的瀏覽會打到的那層，用支援最廣的 WebP；彈窗層用 AVIF
  （同畫質再小三成），不支援的舊瀏覽器由 `modalImgError()` 退回卡片層的 WebP——比較糊
  但看得到。退路鏈寫成函式，不要塞在 `onerror=` 的字串裡（三層就沒法讀了）。
- **⚠ 產物目錄要排除在「來源目錄」之外**。`make_thumbs.py` 的 `EXTS` 含 `.webp`，
  新增 `配裝圖片/卡片/` 之後它把卡片層當成來源圖，在 `縮圖/卡片/` 生了 **237MB 的
  「縮圖的縮圖」**，而且不會報錯。同理 `health_check.py` 的「縮圖覆蓋率」分母也多算了
  7,060 張、永遠顯示只有一半。**加新的圖片產出目錄時，把所有會 `rglob` 圖片的腳本掃一遍。**
- `make_thumbs.py` 另加了「已有同名 `.avif` 且不比來源舊就跳過」——否則 `--drop-jpg`
  清掉中間產物後，下一次跑它會把 611MB 的 `.jpg` 全部生回來。

### 4.37 沒有時間欄位時：先把三個來源查完，再把僅存的訊號**固化進資料檔**（2026-08-28）

幻化配裝圖鑑的預設排序改成「投稿新→舊」之後才發現，**精選 95 套完全沒有時間欄位**
（它們不是投稿、是站方自選）。查來源的順序與結果：

| 來源 | 怎麼查 | 結果 |
|------|--------|------|
| git 歷史 | `git -c core.quotepath=false log --diff-filter=A --name-only` 一次掃整個目錄 | **零分辨力**：95 張圖同一個 commit、JSON 的 95 個 id 同一天。子專案是**一次性匯入**的，原 repo 歷史沒帶過來 |
| EXIF | Pillow `getexif()` ＋ `get_ifd(0x8769)` | **0/95**。壓縮轉檔過的遊戲截圖，EXIF 已被剝掉 |
| 檔案 mtime | `os.path.getmtime` | 有三群（05-24／05-27／06-26），但**不進 git** |

三條實務教訓：

1. **查 git 路徑要先關 `core.quotepath`**。git 預設把非 ASCII 路徑輸出成
   `"tools/glamour/é..."`，拿去跟 JSON 裡的路徑做字串比對會**全部對不到**，
   而且看起來像「這些檔案沒有歷史」——第一次跑就是這樣被騙的。
2. **mtime 是「批次複製時間」不是「建立時間」**，而且**不可攜**（換機 clone 後全變成
   checkout 時間）。實測 #01–#31 的 mtime 全擠在 3 分鐘內、編號序與 mtime 序有 15 處逆序——
   直接拿來排序會得到看起來隨機的順序。**只取到「日」、同日內改用編號分先後**才可用。
3. **僅存的訊號要當場固化進資料檔**。mtime 只存在於「當初做那批圖的那台機器」，
   一旦重新 clone 就永久消失。所以新增 `added` 欄位（`YYYY-MM-DD`）寫進
   `data/curated_outfits.json`，並在腳本檔頭與 `CLAUDE.md` **註明它的來源與精度**——
   免得日後有人把它當成精確的建立時間或拍攝時間。

補上 `added` 之後精選才排得進社群的時間軸（實測落在第 454–915 筆／第 8–16 頁），
而不是整批堆在最後兩頁。缺值的處理是「當成最舊排到最後 ＋ `health_check.py` 報出來」——
**刻意讓它顯眼**，而不是猜一個日期填進去。

- **交叉驗證慣例**：人工製作 28 筆已與 Teamcraft `recipes.json` jobId −10 逐筆比對素材與數量，28/28 一致。日後改動 build-island 後照跑一次。

### 5.9 幻化配裝圖鑑（glamour）：取得方式一律吃 `item_sources.js`，不要信單一 `source` 欄
`curated_outfits.js`／`mirapri_outfits.js`／`official_sets.js` 裡每件裝備的 `source`／`src` 欄**只是「其中一種」取法**——`pipeline.py` 的 `_best()` 取優先度最高那個、`build_sets.py` 的 `fmt_piece_source()` 取前兩條且多副本只寫第一個＋「等N處」。sources.json 有 26% 的裝備是多來源，照這些欄位做篩選／統計會少掉約四成的取法（2026-07-19 使用者回報「明明拿得到卻篩不到」）。
- **完整清單＝`tools/glamour/item_sources.js`**（`build_item_sources.py` 產生，裝備 ID → 正規化來源鍵）。前端 `pieceSrcKeys()`／`entrySrcKeys()` 已封裝好，**任何新功能要用取得方式一律走這兩個函式**，別再讀 `p.source`。
- 來源鍵不含價格／NPC 地點／副本類型，目的是讓官方套裝與配裝兩種寫法收斂成同一個選項；要顯示細節才用原本的 `source`／`src` 字串。
- **重建任何一份前端 js 後必須重跑 `build_item_sources.py`**（`update_all.py` 的 full／local 都已排在 `build_site.py` 之後）。漏跑不會報錯，只會安靜地退回單一來源。
- **頁面狀態同步到網址（History API）**：檢視／篩選／細項／搜尋／排序／頁碼／開啟中的套裝／語言都寫進 query string，瀏覽器上一頁才有東西可回，網址也能分享。**改任何會改變畫面的互動，記得補 `syncURL(true)`**；打字搜尋、彈窗內上下套、關彈窗要用 `syncURL(false)`（replace），否則歷史會被灌爆、或「關掉彈窗後按上一頁又開回來」。兩個踩過的雷：① **Bootstrap modal 在開啟動畫進行中會忽略 `hide()`**（點開後馬上按上一頁關不掉）→ 用 `modalShowing`／`closeAfterShown` 旗標等 `shown` 事件再關；② 判斷彈窗開著**不能看 `.show` class**（非同步才加上去），要用自己維護的 `openModalId`。
- **精選套裝的裝備以 `iid`（道具 ID）為權威**：`data/curated_outfits.json` 每件都已回填 `iid`（2026-07-20，500/500），`build_site.py` 的 `stamp_badges()` 有 id 就用 id，只有沒 id 的新件才退回名稱比對。**原本純靠名稱猜的問題是「猜不到不會報錯」**——該件靜默掉 iid，連帶失去徽章與 `item_sources.js` 的取得方式；改版撞同名或官方改譯名就會踩到。新增套裝時請直接填 `iid`（查名稱時本來就會拿到），或事後跑 `backfill_curated_iid.py --apply`（撞名會拒填並列報告，不亂猜）；`health_check.py` 已會擋缺 id 的件。
- **精選的 `zh`／`ja`／`en`／`patch`／`lv` 一律由 `iid` 從 DB 推導，不手填**：2026-07-20 用 iid 逐件稽核 500 件，抓出 **211 處人工輸入誤差**——版本一律填 7.0（實際 7.3/7.4/7.5）、等級多半留在預設 Lv.1（152 件）、日文名濁點長音抄錯（`バルチザン`→`パルチザン` 等 18 件）、英文名由另一語言回譯（19 件），最嚴重的是**台服未實裝卻填自編繁中名 11 件**，害 5 套被誤標「🇹🇼 繁中版可幻化」（違反 §4「繁中名絕不自己翻」）。對照組：社群配裝 33705 件同樣稽核只有 0.1% 不符、日文名 0 不符——**問題全出在人工輸入，不是資料來源**。已由 `build_site.py` 的 `apply_db_fields()` 每次建置重算，並有 `normalize_curated_from_db.py` 做一次性校正。
- **`job`（職業限制）也由 `cjc` 推導，不手填**：2026-07-20 稽核出手填 job 一堆錯——自創詞「偵察職業」（cjc 103 ROG NIN VPR，正解＝忍者、劍蛇師）、把整職能寫成單一職業、只列部分職業、專武填錯職能（月讀太刀填「盾衛職業」實為暗黑騎士專武 DRK）。`build_site.job_from_cjc()` 是唯一權威：整職能→群組名、真子集→列具體職業、全戰鬥→全職業、Disciple of Hand/Land→製作/採集。cjc id→職業字串在 `data/xivapi_sets_cache.json` 的 `cjc_names`（build_sets.py 產出）。前端 `jobCodes()` 會把「忍者、劍蛇師」用 `、` 拆開查 JOB_CODES，所以顯示字串換法不影響繁中版可幻化判定。
- **「部位對不上」是內容錯，不能自動修**：#01 腳部原本填了腿部道具「寄葉五五式禦敵軍褲」。看圖判讀後確認腿部已被「男爵及膝褲」佔用（染色標籤煤玉黑／羅蘭莓與圖上紅裙黑腰帶吻合），圖上那雙過膝長靴是同系列的**「寄葉五五式禦敵軍靴」(33566, YoRHa Type-55 **Thighboots**)**——投稿者標的是同系列的「脚衣」而非「軍靴」。這類錯誤 `health_check.py` 現在會擋（比對 DB 部位），但**修正一律要看圖，別照名稱猜**。
- **取得方式的分類按鈕與細項下拉必須吃同一份來源**（都走 `entryStSet()`／`entrySrcKeys()`）。2026-07-19 曾因分類只看整套那一種 st、細項看完整鍵而互斥：「夢幻套裝」整套來源是 🗓️Starlight Celebration（st=event）但件是 🪙夢幻帽布料 兌換，同時選「代幣兌換」＋該細項會篩出 0 筆。改法是分類也取完整來源鍵的 st 聯集，讓「細項 ⊆ 分類」恆成立（已用全鍵稽核驗過 0 例外）。卡片上的 tag 徽章仍顯示主要來源，不跟著放寬。
